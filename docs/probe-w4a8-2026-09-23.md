# W4A8 on the mixed 4-bit × 8-bit k32 DPAS - probe results (2026-09-23)

**Verdict: REJECTED, on both of the two questions design §2 said had to be
answered separately.** The W4A8 GEMM runs at **1.017×** the same-shape bf16
two-pass control and **0.965×** once the activation quantiser it requires is
counted - against a pre-registered bar of **1.53×**. And on real weights and
real activations its output is **2.79 % away from the bf16 result in relative
L2**, with a worst-row cosine of **0.9976**, below the 0.999 bar this project
uses for every tensor comparison. Design §7 **branch 1** applies: recorded, not
tuned. W4A16 stands and the parity program's S2-S5 remain the whole plan.

Pre-registration: `docs/superpowers/specs/2026-09-22-w4a8-dpas-probe-design.md`.
Rate landscape this rests on: `docs/probe-dpas-rates-2026-09-22.md`. The
same-shape control and the cautionary tale: `docs/probe-fused-dequant-2026-09-22.md`.

Every number below is **measured** unless marked **derived**.

## 1. The break-even, restated before the numbers

From design §4, fixed before this probe's source existed and unchanged since:

| outcome | W4A8 time for the shape | implication |
|---|---:|---|
| break-even | **5.341 ms** | no reason to continue |
| **worth a study** | **≤ 3.5 ms (≥ 1.53×)** | linear path ≈ 1060 ms, −560 ms |
| the instruction's promise | 2.67 ms (2.00×) | linear path ≈ 810 ms, −810 ms |

Shape: gate‖up, K = 5120, N = 34816, M = 2048, **730.1 GFLOP** per call
(derived: 2 × 2048 × 5120 × 34816). The 5.341 ms is
`docs/probe-fused-dequant-2026-09-22.md`'s control - `pf_dequant_slab` 0.826 ms
+ `pf_gemm_T0` 4.515 ms, 136.72 TFLOP/s effective.

**The probe fails below 1.53× and that is recorded rather than tuned away.** It
failed. No tuning pass was run and none is proposed.

### 2.1 The operand-slot deviation from §3's pseudocode

§3 spells the instruction `intel_sub_group_i4_i8_matrix_mad_k32(w_s4, x_s8,
acc)` - weights in the **A** slot. This probe issues
**`intel_sub_group_i8_i4_matrix_mad_k32(x_s8, w_s4, acc)`** - the same mixed
4-bit × 8-bit k32 DPAS with the weights in the **B** slot. §3's prose
requirement is met either way ("the existing int4 symmetric g64 values …  fed as
the 4-bit operand"), and the two spellings are the same instruction rate:
`i4_i8` **366.89 TIOP/s** and `i8_i4` **366.90** (`probe-dpas-rates` §4), the
same number to 0.01 %. That record already named this one:

> "in a GEMM the weights are the B operand, so the builtin a W4A8 kernel would
> actually issue is `i8_i4_k32`, and it measures the same."
> - `docs/probe-dpas-rates-2026-09-22.md` §7

It is not a free choice. The DPAS B (Src1) operand is column-per-lane with K
packed into dwords, so a lane's 32-k 4-bit fragment is **four consecutive
qweight words of its own column** - the checkpoint's layout-0 bytes verbatim,
one `xor` from signed nibbles (§5 shows the 16 `xor` and nothing else). The A
(Src2) operand is distributed the other way, so weights in the A slot would
need a nibble transpose across lanes, and the probe would then have measured
that transpose instead of the rescale it exists to price. **The break-even is
unaffected: both spellings run at the same measured 2.000× of bf16.** Nothing
else in §3 is changed - the weights are the checkpoint's own bytes, only the
activations are quantised, the accumulation is int32 within a group of 64
(exactly two k32 instructions), and the rescale is at every group boundary with
`(wscale[g][n] * xscale[m])` as the multiplier, **not** with `xscale[m]`
factored out to the epilogue, which would have been a cheaper expression than
the one pre-registered. §6 below prices that factoring as a derived number.

## 3. Real weights and real activations (design §5)

Both come from one real prefill, not from a generator.

- **Checkpoint**: `urakozz/Qwen3.8-27B-W4A16-g64-AutoRound-GPTQ`, snapshot
  `84575a18f209992ef96d819b31f924b489e3d55d` - the gate checkpoint, int4 g64
  symmetric, through the production `loader::load` (12.6 s, 18.087 GB, 0
  unconsumed tensors).
- **Weights**: **layer 63's `gate‖up`**, `[5120][34816]` int4 layout 0 plus its
  f16 `[80][34816]` group scales, read back off the device exactly as the
  loader left them. No repack, no re-quantisation.
- **Activations**: the first **2048 ids of `tests/golden/prompts/long.ids`**
  prefilled through `runtime::Engine::prefill` on the L0 backend at C = 2048 -
  one full chunk - and the gate‖up A operand that walk computed for layer 63
  (`PrefillScratch::mixer_out`, the post-attention RMSNorm output the fused
  gate‖up GEMM reads). Captured once to a 115,671,076-byte file and reused by
  every arm.
  Captured statistics: **max|x| 54.75, mean|x| 0.839, 10,479,267 / 10,485,760
  non-zero** - an RMSNorm output with outliers, which is the point.

Weights and activations are therefore the *same* layer of the *same* forward
pass, which is the strongest pairing available without editing a production
file (none was edited).

loses.

0.297 ms it is 5.5 % of the control, and setting it to zero leaves W4A8 at
1.017×.

## 5. Compiler evidence (design §6)

Dumped with `IGC_ShaderDumpEnable=1 IGC_DumpToCustomDir=… ocloc compile …` on
the identical command line CMake uses (`-cl-std=CL3.0
-cl-fp32-correctly-rounded-divide-sqrt -cl-intel-256-GRF-per-thread`,
`-device bmg-g31`), reading `*_simd16_entry_0002.asm` - the final GEN assembly.

| check | required | `pw4a8_gemm` |
|---|---|---|
| `simd_size` | 16 | **16** |
| `grf_count` | 256 | **256** |
| `has_dpas` | true | **true** |
| `spill_mem_size` / `private_size` | absent | **absent** |
| `dpas` per group boundary | 8 blocks × 2 = 16 | **16** |
| `dpas` anywhere else in the kernel | 0 | **0** |
| 4-bit operand native, no widening | `:s4` | **`:s4`** |
| 8-bit operand native, no widening | `:b` | **`:b`** |

`scratch` appears only as `//.declare %scratchloc (35) … IsBuiltin`, the
universal per-kernel ABI declaration every gated kernel in this tree carries;
the authoritative spill signals are absent from the `.zeinfo`. **Spill/fill
bytes: zero.**

**The dpas, verbatim** (operand order `dst src0(acc) src1(B) src2(A)`; the first
eight of a group take `null:d` as src0 because IGC folded the int32 accumulator's
zero initialisation into the instruction, so a group costs no accumulator
clear):

```
dpas.8x8 (16|M0)  r94:d  null:d  r38:s4   r6.0:b   {Atomic,$15.dst}
dpas.8x8 (16|M0)  r86:d  null:d  r38:s4   r10.0:b  {Atomic}
dpas.8x8 (16|M0)  r78:d  null:d  r38:s4   r14.0:b  {Atomic}
dpas.8x8 (16|M0)  r70:d  null:d  r38:s4   r18.0:b  {$15}
…
dpas.8x8 (16|M0)  r94:d  r94:d   r118:s4  r22.0:b  {Atomic,$15.dst}
```

`r38:s4` is the weight fragment - **native 4-bit on a single `dpas.8x8`**, not
widened to bytes and not expanded into two instructions - and `r6.0:b` is the
int8 activation fragment. Sixteen such instructions per group of 64, eight
`{Atomic}`-chained pairs, and no `dpas` outside the group loop.

**2D block messages in the group loop**: 2 data loads + 1 prefetch on the
weight side (`load_block2d.ugm.d32.a64` ×2, `…d32.a64.ca.ca` ×1) and 1 data
load + 1 prefetch on the activation side (`…d16.a64`, `…d16.a64.ca.ca`). The
16 `xor` are the whole int4 zero-point conversion - `q ^ 8` read as a signed
nibble *is* `q − 8`, and the dpas sign-extends `:s4` itself. **There is no
dequant sequence in this kernel at all**: no `shl`/`asr` chain, no `mov … :bf`,
nothing. That half of the idea worked exactly as designed.

### 5.1 The rescale sequence - the cost §3 warned about

The group loop's instruction histogram (lines 744-1033 of the `.asm`, the single
backward-branching loop):

| | count |
|---|---:|
| `dpas.8x8` | **16** |
| SIMD16 float instructions | **194** |
| &nbsp;&nbsp;`mov (16\|M0) …:f ← …:d` (the int32→float convert) | **64** |
| &nbsp;&nbsp;`mul (16\|M0) …:f` (`wscale[g][n] * xscale[m]`) | **64** |
| &nbsp;&nbsp;`mad (16\|M0) …:f` (the fp32 accumulate) | **64** |
| `xor` (the int4 zero-point fold) | 16 |
| everything else (`add`/`shl`/`cmp`/`asr`/`macl`/`mach`, addressing + loop control) | 26 |

**Twelve SIMD16 instructions per `dpas.8x8`.** The rescale is three of them per
output element per group boundary, and the assembly shows exactly the three §3
asks for, verbatim and contiguous:

```
mov (16|M0)  r6.0<1>:f    r94.0<1;1,0>:d                      // (float)acc_i32
mul (16|M0)  acc0.0<1>:f  r2.1<0;1,0>:f  r7.0<1;1,0>:f        // xscale[m] (uniform) * wscale[g][n] (per lane)
mad (16|M0)  r174.0<1>:f  r174.0<1;0>:f  acc0.0<1;0>:f  r6.0<1>:f   // out_f32 += …
```

`r2.1<0;1,0>:f` is the broadcast of a sub-group-uniform `xscale[m]` (the row is
the dpas repeat index, so it is a scalar per component) and `r7.0<1;1,0>:f` is
the per-lane `wscale[g][n]` (the column is the lane). The product cannot be
hoisted: there is a distinct value for every (row, column) and it changes at
every group.

**Per group boundary, per sub-group: 192 SIMD16 float instructions against 16
`dpas.8x8`.** That is the number this probe exists to produce.

## 6. What the numbers mean - the rescale, priced

Cycle accounting, **derived** from the measured 5.440 ms and the measured DPAS
issue rate (16.0 EU-cycles per `dpas.8x8`, `probe-dpas-rates` §4), at 256 EUs
and 2.8 GHz:

| quantity | value |
|---|---:|
| sub-group × group iterations in the launch (derived: 64 × 1088 × 80) | 5,570,560 |
| EU-cycles in 5.440 ms (derived) | 3.900 × 10⁹ |
| **EU-cycles per iteration** (derived) | **700** |
| of which `dpas` (derived: 16 × 16.0) | **256** (36.6 %) |
| of which everything else (derived) | **444** (63.4 %) |
| non-dpas instructions in the loop | 194 SIMD16 float + 52 scalar + 6 block2d/send |

The pure-DPAS floor for this shape is **1.990 ms** (derived: 730.1 GFLOP /
366.9 TIOP/s), and 256 / 700 × 5.440 = 1.99 ms - the two agree, so the cycle
model is the measurement rather than a story about it.

**The finding: the rescale ALU does not hide under the XMX pipe.** 700 cycles is
256 + 444, i.e. the matrix pipe and the float pipe are essentially **additive**
on this kernel. That is exactly the failure mode
`docs/probe-fused-dequant-2026-09-22.md` recorded when it moved dequant ALU into
a mainloop: same class of risk, named in the brief, landed the same way.

**How much of the 444 is the rescale** depends on what the 52 scalar `(W)`
address/loop instructions and the 6 memory messages cost, which this probe did
not measure separately. The band is narrow either way:

| attribution | cycles per SIMD16 float instruction | rescale share of the 444 | rescale share of the 5.440 ms |
|---|---:|---:|---:|
| all 444 cycles to the 194 float instructions | 2.29 | 440 | **3.42 ms** |
| 1 cycle each to the 52 scalars and 6 messages | 2.00 | 384 | **2.98 ms** |

**The per-group rescale costs between 3.0 and 3.4 of the 5.440 ms.** The matrix
math it rescales costs 1.99 ms.

### 6.1 Three counterfactuals, all derived, none measured

Stated so that the obvious "but what if..." questions are answered without a
tuning pass. Each row removes instructions from the 700-cycle iteration at the
two attributions above and rescales the measured 5.440 ms by the result; the
0.297 ms quantiser is added unchanged.

| variant | rescale instrs / group / sub-group | derived GEMM ms | derived total ms | derived × control |
|---|---:|---:|---:|---:|
| **as pre-registered and measured** | 192 | **5.440** | **5.736** | **0.965×** (measured) |
| `xscale[m]` factored out to the epilogue (drops the 64 `mul`) | 128 | 4.30 - 4.45 | 4.60 - 4.74 | **1.17× - 1.20×** |
| one instruction per output element per group (no such sequence exists) | 64 | 3.16 - 3.45 | 3.46 - 3.75 | 1.48× - 1.60× |
| rescale entirely free - the instruction's ceiling | 0 | 2.00 - 2.46 | 2.30 - 2.75 | 2.01× - 2.41× |

Three things to read off it.

1. **The ceiling was real.** With the rescale free the kernel lands at
   2.0× - 2.4×, i.e. the measured DPAS rate does deliver what
   `probe-dpas-rates` said it would. Nothing about the weights, the memory or
   the operand widths is the problem.
2. **The one obvious algebraic saving does not rescue it.** `xscale[m]` is
   constant in `k`, so it could be applied once in the epilogue instead of at
   every group boundary - a different expression from the pre-registered one,
   and a cheaper one. It reaches **1.17× - 1.20×**, still far below 1.53×. This
   probe therefore closes that question without running the arm.
3. **What this does NOT claim.** The one-instruction-per-output row straddles
   the bar (1.48× - 1.60×), so the probe does **not** claim that no conceivable
   group handling could ever reach 1.53×. It claims that the pre-registered one
   misses by 0.57× and the obvious saving on it misses by 0.33× - and that any
   candidate must fit the *entire* non-dpas body, addressing and loop control
   included, into roughly 84 SIMD16 instructions per group per sub-group, when
   the accumulator alone is 64 SIMD16 registers wide and the loop already
   spends 52 scalar instructions on addressing.

The shape is what forces it: at group 64 with a k32 instruction a group
boundary arrives every **two** dpas, and each dpas-block carries 8 × 16 outputs,
so the boundary touches 64 SIMD16 registers of accumulator per 16 dpas - a 4:1
instruction ratio before a single useful operation is chosen.

## 7. Error against the bf16 two-pass result (design §5)

Same real weights, same real activations, same process, compared over all
**71,303,168** fp32 outputs against the control's own output.

| metric | value |
|---|---:|
| max relative error, all outputs | 7.2 × 10⁶ (at row 45 col 5503, where the bf16 value is **1.86 × 10⁻⁸** - a denominator artefact, quoted so it cannot hide) |
| **max relative error**, outputs above 1 % of their row RMS | **26.48** |
| **mean relative error** over those 70,563,326 outputs | **0.0965** |
| max absolute error | 1.095 |
| **global relative L2**, ‖W4A8 − bf16‖ / ‖bf16‖ | **0.02786** |
| per-row cosine, mean | 0.999579334 |
| **per-row cosine, worst row** | **0.997621824** (row 870) |
| rows whose largest output moved to another column | **5 / 2048** |
| mean top-8 column overlap per row | 0.9844 |

This is **not** a small error. The project's standing tensor bar is a cosine of
**0.999** (`tests/golden/golden_common.h`), and the worst row of a *single*
linear in a *single* layer is already **0.9976** - before 63 more layers of it.
Five of 2048 tokens have a different largest gate‖up output. Design §7's branch
3 ("≥ 1.53× with large error → report both numbers and stop") would have applied
had the rate passed; it did not, so branch 1 applies and this table is
corroboration rather than the deciding evidence.

**The error is exactly what the dynamic range predicts, not a bug.** For
symmetric per-token int8, the output's relative error is ≈ (max|x| / 440) /
rms|x| (derived: quantisation step `max|x|/127`, uniform noise, √12). With this
chunk's measured scales that is ≈ 2.8 %, and the measurement is 2.79 %. The
kernel is also verified against an **integer-exact CPU oracle** over a 32 × 32
slice at full K - max |device − host| = **0** (§9) - so the arithmetic is the
one §3 specifies and the error is the quantisation's, not the kernel's.

## 8. The activation dynamic range (design §5)

max|x| over median|x|, per token, over the chunk's 2048 real tokens:

| statistic | value |
|---|---:|
| min | 6.8 |
| **median** | **44.9** |
| p90 | 66.4 |
| p99 | 88.4 |
| **max** | **111.2** |
| per-token int8 scale (max\|x\|/127): min / max | 0.0431 / 0.4311 |

**This is the number that transfers, and it is bad.** A ratio of 44.9 means the
*median* activation lands about `127 / 44.9 ≈ 2.8` quantisation steps from
zero: half of every token's 5120 values are represented by three levels or
fewer. That is a property of this model's post-attention RMSNorm output, not of
this layer or this prompt, so any other linear fed by a normed residual should
be expected to behave the same way.

**Read-through to design §8 (W4A4, explicitly out of scope here).** §8 said this
probe's error numbers are the evidence that decides whether W4A4 is worth
asking about. They say no, on both halves.

*Error.* int4 activations are 16× coarser than the int8 measured here, on a
distribution whose median already sits under three int8 levels. The 2.79 %
relative L2 and the 0.9976 worst-row cosine above are the *optimistic* case.

*Rate (derived, and conditional on the same rescale).* `i4_i4_k64` does halve
the number of group boundaries - K = 64 per instruction, so **one** dpas per
g64 group instead of two - which takes the dpas share of a group iteration from
256 cycles to 128 while leaving the 444 non-dpas cycles exactly where they are.
572 cycles instead of 700, i.e. a derived **4.45 ms** for this shape, **≈1.24×**
the control, and an efficiency against its own 4× ceiling of **22 %** rather
than W4A8's 37 %. It does not reach 1.53× either, and it needs an int4
activation quantiser on top. **No W4A4 kernel was written and none is
proposed.**

## 9. Dispatch proof

A record was claimed on this box this week for a kernel that had not run. The
W4A8 arm therefore proves twice, at run time, that it executed `pw4a8_gemm`:

```
| module the W4A8 arm opened | `/home/user/b70-inference-server/build/kernels/pw4a8.bin` |
| `zeKernelGetName` on the handle `launch()` receives | **`pw4a8_gemm`** |
| `zeKernelGetName`, quantiser handle | `pw4a8_quant` |
| `zeKernelGetName`, control GEMM handle | `pf_gemm` |
| `zeKernelGetName`, control dequant handle | `pf_dequant_slab` |
| signature word the executed kernel wrote | **0x57344138** (expected 0x57344138 = 'W4A8') |
```

The first is `zeKernelGetName` on the **same `ze_kernel_handle_t`** that
`runtime::prefill::Context::launch` receives - not on a name the host looked up
separately - and the probe throws if it is not `pw4a8_gemm`. The second is
device-side: `pw4a8_gemm` writes `'W4A8'` into a shared-memory word from one
work-item, and the host reads it back after the arm and throws if it is absent.
The control's two handles are printed beside them so the whole dispatch is
visible in one table.

A third, independent check that the *right* kernel ran the *right* arithmetic:

```
## the kernel computes design §3's arithmetic (integer-exact CPU oracle, 32 × 32 slice)
max |device - host| over the slice: 0
```

The host recomputes 1024 outputs at full K = 5120 from the raw GPTQ nibbles and
the device's own int8 activations and per-token scales, in the same group order
with the same `fma`. It agrees **bit for bit**. A transposed or mis-packed DPAS
operand cannot produce that by accident, so this doubles as the operand-layout
evidence behind §5's `:s4` / `:b` line.

## 11. Decision

**Design §7, branch 1: `< 1.53×` → rejected, recorded, W4A16 stands and the
parity program's S2-S5 remain the whole plan.**

- 0.965× of the control measured here, 0.931× of the pre-registered 5.341 ms
  bar, against a 1.53× bar. The gap is not close and no tile, group-handling or
  tolerance change was attempted.
- **No adoption spec is written.** The §7 branch-2 work - the W4A8 CPU oracle,
  task-level acceptance, and what happens to `prefill_gate`,
  `prefill_consistency`, `prefill_determinism` and
  `prefill_backend_equivalence_test` - is not started, because the numbers do
  not reach it.
- No production file was edited and none is proposed. `pf_gemm.cl`,
  `pf_dequant_slab.cl` and `runtime::prefill::linear_l0` are untouched.
- The error table and the dynamic range stand on their own as the answer to
  design §8's W4A4 question: **don't ask it** (§8 above).

**What this probe does NOT license.** It measured one shape, one layer, one
prompt, one tile (256 × 128 with a 32 × 32 sub-group tile) and one group size
(the checkpoint's 64). It does not rule on: a checkpoint quantised at a larger
group, which is the only change that moves §6.1's 4:1 ratio and would need a new
checkpoint and its own probe; per-channel or static activation scales, which
change the error question and not the rate one; or any shape whose N is small
enough that the accumulator pressure §6 describes disappears. Each of those is a
**new** probe with a new break-even, not a tuning pass on this one.

- `tools/probe/probe_w4a8.cl` - new, probe-only. Two entry points: `pw4a8_gemm`
