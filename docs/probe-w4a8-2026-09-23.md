# W4A8 on the mixed 4-bit by 8-bit DPAS: rejected (2026-09-23)

**Verdict: REJECTED, on both of the two questions that had to be answered
separately.**

The W4A8 GEMM runs at **1.017x** the same-shape bf16 two-pass control, and
**0.965x** once the activation quantiser it requires is counted, against a bar
of **1.53x** fixed before the probe's source existed. And on real weights and
real activations its output is **2.79% away from the bf16 result in relative
L2**, with a worst-row cosine of **0.9976**, below the 0.999 bar this project
uses for every tensor comparison.

W4A16 stands. Recorded, not tuned.

The rate landscape this rests on is
[probe-dpas-rates-2026-09-22.md](probe-dpas-rates-2026-09-22.md). The
same-shape control and the cautionary tale it repeats are in
[probe-fused-dequant-2026-09-22.md](probe-fused-dequant-2026-09-22.md).

Every number below is **measured** unless marked **derived**.

## 1. The break-even, stated before the numbers

Fixed before this probe's source existed and unchanged since:

| outcome | W4A8 time for the shape | implication |
|---|---:|---|
| break-even | **5.341 ms** | no reason to continue |
| **worth a study** | **3.5 ms or less, 1.53x or better** | linear path about 1060 ms, -560 ms |
| the instruction's promise | 2.67 ms, 2.00x | linear path about 810 ms, -810 ms |

Shape: gate‖up, K = 5120, N = 34816, M = 2048, **730.1 GFLOP** per call
(derived: 2 x 2048 x 5120 x 34816). The 5.341 ms is the fused-dequant probe's
control: slab dequant 0.826 ms plus GEMM 4.515 ms, 136.72 TFLOP/s effective.

**It failed.** No tuning pass was run.

## 2. Two deviations from the design as written

**One card, not the other.** The card this probe family normally runs on was
down: `zeInit` segfaulting on it, which this probe did not reproduce and does
not claim as its own measurement. What was verified is the consequence:
`clinfo -l` enumerated **one** Arc Pro B70, not two. Everything here ran on the
remaining card, and a buffer smoke test exited 0 on it immediately before and
immediately after the timed arms. Every arm ran in the foreground on an
otherwise idle box, one job at a time.

**Weights in the B operand slot, not the A slot.** The design spelled the
instruction `intel_sub_group_i4_i8_matrix_mad_k32(w_s4, x_s8, acc)`, weights in
**A**. This probe issues **`intel_sub_group_i8_i4_matrix_mad_k32(x_s8, w_s4,
acc)`**, the same mixed 4-bit by 8-bit DPAS with the weights in **B**. The
requirement is met either way, and the two spellings are the same instruction
rate: `i4_i8` measures 366.89 TIOP/s and `i8_i4` 366.90, the same number to
0.01%.

It is not a free choice. The DPAS B operand is column-per-lane with K packed
into dwords, so a lane's 32-k 4-bit fragment is **four consecutive qweight
words of its own column**, which is the checkpoint's layout-0 bytes verbatim,
one `xor` away from signed nibbles. The A operand is distributed the other way,
so weights in the A slot would need a nibble transpose across lanes, and the
probe would then have measured that transpose instead of the rescale it exists
to price. **The break-even is unaffected: both spellings run at the same
measured 2.000x of bf16.**

Nothing else changed. The weights are the checkpoint's own bytes, only the
activations are quantised, the accumulation is int32 within a group of 64
(exactly two k32 instructions), and the rescale happens at every group boundary
with `(wscale[g][n] * xscale[m])` as the multiplier rather than with
`xscale[m]` factored out to the epilogue. That factoring would have been the
cheaper expression, and section 6.1 prices it as a derived number.

## 3. Real weights and real activations

Both come from one real prefill, not from a generator.

- **Checkpoint**: `urakozz/Qwen3.8-27B-W4A16-g64-AutoRound-GPTQ`, snapshot
  `84575a18f209992ef96d819b31f924b489e3d55d`, the gate checkpoint, int4 g64
  symmetric, through the production loader (12.6 s, 18.087 GB, 0 unconsumed
  tensors).
- **Weights**: **layer 63's `gate‖up`**, `[5120][34816]` int4 layout 0 plus its
  f16 `[80][34816]` group scales, read back off the device exactly as the
  loader left them. No repack, no re-quantisation.
- **Activations**: the first **2048 ids of the long golden prompt** prefilled
  through the real engine on the Level Zero backend at chunk width 2048, one
  full chunk, and the gate‖up A operand that walk computed for layer 63, which
  is the post-attention RMSNorm output the fused gate‖up GEMM reads. Captured
  once to a 115,671,076-byte file and reused by every arm. Captured statistics:
  **max|x| 54.75, mean|x| 0.839, 10,479,267 of 10,485,760 non-zero**, an
  RMSNorm output with outliers, which is the point.

Weights and activations are therefore the *same* layer of the *same* forward
pass, the strongest pairing available without editing a production file. None
was edited.

## 4. The three rates

Level Zero kernel timestamps, best of 5 after one discarded warm-up, the same
harness the fused-dequant probe used, so the control row is comparable to the
one the break-even came from.

| arm | launches | kernel ms | rate | vs the control |
|---|---:|---:|---:|---:|
| **bf16 two-pass control**, 34 slabs | 68 | **5.534** | 131.94 TFLOP/s | 1.000x |
| of which slab dequant | 34 | 0.843 | | |
| of which GEMM | 34 | 4.691 | | |
| **W4A8 GEMM** | 1 | **5.440** | 134.23 TOP/s | **1.017x** |
| **activation quantiser** | 1 | **0.297** | 106.0 GB/s | |
| **W4A8 total**, quantiser plus GEMM | 2 | **5.736** | 127.28 TOP/s | **0.965x** |

Repeat run, same binaries, minutes apart: control **5.529**, W4A8 **5.438**,
quantiser **0.296**, total **5.734**, a spread of **0.1%** on every row. The
error table reproduced digit for digit; the kernels are deterministic.

Against the **5.341 ms** bar rather than against this process's own control,
W4A8 is **0.931x**. Either denominator is far below 1.53x, so the verdict does
not turn on the choice.

**The control is 3.6% slower here than the 5.341 ms it measured in the
fused-dequant probe.** That probe ran on the other card; this one could not.
It is recorded rather than explained away, and it moves the control in the
direction that would *help* W4A8, which still loses.

The quantiser is **not** optimised and is not the reason for anything: at
0.297 ms it is 5.5% of the control, and setting it to zero leaves W4A8 at
1.017x.

## 5. Compiler evidence

Shader dumps on the identical command line the build uses, reading the final
Xe2 assembly.

| check | required | measured |
|---|---|---|
| `simd_size` | 16 | **16** |
| `grf_count` | 256 | **256** |
| `has_dpas` | true | **true** |
| `spill_mem_size` / `private_size` | absent | **absent** |
| `dpas` per group boundary | 8 blocks x 2 = 16 | **16** |
| `dpas` anywhere else in the kernel | 0 | **0** |
| 4-bit operand native, no widening | `:s4` | **`:s4`** |
| 8-bit operand native, no widening | `:b` | **`:b`** |

`scratch` appears only as the universal per-kernel ABI declaration every gated
kernel in this tree carries; the authoritative spill signals are absent from
the metadata. **Spill and fill bytes: zero.**

**The `dpas`, verbatim** (operand order `dst src0(acc) src1(B) src2(A)`; the
first eight of a group take `null:d` as src0 because the compiler folded the
int32 accumulator's zero initialisation into the instruction, so a group costs
no accumulator clear):

```
dpas.8x8 (16|M0)  r94:d  null:d  r38:s4   r6.0:b   {Atomic,$15.dst}
dpas.8x8 (16|M0)  r86:d  null:d  r38:s4   r10.0:b  {Atomic}
dpas.8x8 (16|M0)  r78:d  null:d  r38:s4   r14.0:b  {Atomic}
dpas.8x8 (16|M0)  r70:d  null:d  r38:s4   r18.0:b  {$15}
…
dpas.8x8 (16|M0)  r94:d  r94:d   r118:s4  r22.0:b  {Atomic,$15.dst}
```

`r38:s4` is the weight fragment, **native 4-bit on a single `dpas.8x8`**, not
widened to bytes and not expanded into two instructions, and `r6.0:b` is the
int8 activation fragment. Sixteen such instructions per group of 64, eight
chained pairs, and no `dpas` outside the group loop.

**2D block messages in the group loop**: 2 data loads plus 1 prefetch on the
weight side, 1 data load plus 1 prefetch on the activation side. The 16 `xor`
are the whole int4 zero-point conversion: `q ^ 8` read as a signed nibble *is*
`q - 8`, and the `dpas` sign-extends `:s4` itself. **There is no dequant
sequence in this kernel at all**: no shift chain, no bf16 conversion, nothing.
That half of the idea worked exactly as designed.

### 5.1 The rescale sequence, which is the cost

The group loop's instruction histogram, from the single backward-branching
loop:

| | count |
|---|---:|
| `dpas.8x8` | **16** |
| SIMD16 float instructions | **194** |
| of which `mov …:f <- …:d`, the int32 to float convert | **64** |
| of which `mul …:f`, `wscale[g][n] * xscale[m]` | **64** |
| of which `mad …:f`, the fp32 accumulate | **64** |
| `xor`, the int4 zero-point fold | 16 |
| everything else: addressing and loop control | 26 |

**Twelve SIMD16 instructions per `dpas.8x8`.** The rescale is three of them per
output element per group boundary, and the assembly shows exactly those three,
verbatim and contiguous:

```
mov (16|M0)  r6.0<1>:f    r94.0<1;1,0>:d                      // (float)acc_i32
mul (16|M0)  acc0.0<1>:f  r2.1<0;1,0>:f  r7.0<1;1,0>:f        // xscale[m] (uniform) * wscale[g][n] (per lane)
mad (16|M0)  r174.0<1>:f  r174.0<1;0>:f  acc0.0<1;0>:f  r6.0<1>:f   // out_f32 += …
```

`r2.1<0;1,0>:f` is the broadcast of a sub-group-uniform `xscale[m]`, since the
row is the `dpas` repeat index, and `r7.0<1;1,0>:f` is the per-lane
`wscale[g][n]`, since the column is the lane. The product cannot be hoisted:
there is a distinct value for every row and column pair and it changes at every
group.

**Per group boundary, per sub-group: 192 SIMD16 float instructions against 16
`dpas.8x8`.** That is the number this probe exists to produce.

## 6. The rescale, priced

Cycle accounting, **derived** from the measured 5.440 ms and the measured DPAS
issue rate of 16.0 EU-cycles per `dpas.8x8`, at 256 EUs and 2.8 GHz:

| quantity | value |
|---|---:|
| sub-group by group iterations in the launch (derived: 64 x 1088 x 80) | 5,570,560 |
| EU-cycles in 5.440 ms (derived) | 3.900e9 |
| **EU-cycles per iteration** (derived) | **700** |
| of which `dpas` (derived: 16 x 16.0) | **256** (36.6%) |
| of which everything else (derived) | **444** (63.4%) |
| non-dpas instructions in the loop | 194 SIMD16 float, 52 scalar, 6 memory |

The pure-DPAS floor for this shape is **1.990 ms** (derived: 730.1 GFLOP /
366.9 TIOP/s), and 256 / 700 x 5.440 = 1.99 ms. The two agree, so the cycle
model is the measurement rather than a story about it.

**The finding: the rescale ALU does not hide under the XMX pipe.** 700 cycles
is 256 plus 444, so the matrix pipe and the float pipe are essentially
**additive** on this kernel. That is exactly the failure mode the fused-dequant
probe recorded when it moved dequant ALU into a mainloop: same class of risk,
named in advance, landed the same way.

**How much of the 444 is the rescale** depends on what the 52 scalar addressing
and loop instructions and the 6 memory messages cost, which this probe did not
measure separately. The band is narrow either way:

| attribution | cycles per SIMD16 float instruction | rescale share of 444 | rescale share of 5.440 ms |
|---|---:|---:|---:|
| all 444 cycles to the 194 float instructions | 2.29 | 440 | **3.42 ms** |
| 1 cycle each to the 52 scalars and 6 messages | 2.00 | 384 | **2.98 ms** |

**The per-group rescale costs between 3.0 and 3.4 of the 5.440 ms.** The matrix
math it rescales costs 1.99 ms.

### 6.1 Three counterfactuals, all derived, none measured

Stated so the obvious "but what if" questions are answered without a tuning
pass. Each row removes instructions from the 700-cycle iteration at the two
attributions above and rescales the measured 5.440 ms by the result; the
0.297 ms quantiser is added unchanged.

| variant | rescale instrs / group / sub-group | derived GEMM ms | derived total ms | derived x control |
|---|---:|---:|---:|---:|
| **as measured** | 192 | **5.440** | **5.736** | **0.965x** (measured) |
| `xscale[m]` factored out to the epilogue, dropping the 64 `mul` | 128 | 4.30 to 4.45 | 4.60 to 4.74 | **1.17x to 1.20x** |
| one instruction per output element per group; no such sequence exists | 64 | 3.16 to 3.45 | 3.46 to 3.75 | 1.48x to 1.60x |
| rescale entirely free, the instruction's ceiling | 0 | 2.00 to 2.46 | 2.30 to 2.75 | 2.01x to 2.41x |

Three things to read off it.

1. **The ceiling was real.** With the rescale free the kernel lands at 2.0x to
   2.4x, so the measured DPAS rate does deliver what the rate probe said it
   would. Nothing about the weights, the memory or the operand widths is the
   problem.
2. **The one obvious algebraic saving does not rescue it.** `xscale[m]` is
   constant in `k`, so it could be applied once in the epilogue instead of at
   every group boundary, a cheaper expression than the one measured. It reaches
   **1.17x to 1.20x**, still far below 1.53x. This probe therefore closes that
   question without running the arm.
3. **What this does NOT claim.** The one-instruction-per-output row straddles
   the bar at 1.48x to 1.60x, so the probe does **not** claim that no
   conceivable group handling could ever reach 1.53x. It claims that the one
   measured misses by 0.57x and the obvious saving on it misses by 0.33x, and
   that any candidate must fit the *entire* non-dpas body, addressing and loop
   control included, into roughly 84 SIMD16 instructions per group per
   sub-group, when the accumulator alone is 64 SIMD16 registers wide and the
   loop already spends 52 scalar instructions on addressing.

The shape is what forces it: at group 64 with a k32 instruction, a group
boundary arrives every **two** `dpas`, and each `dpas` block carries 8 by 16
outputs, so the boundary touches 64 SIMD16 registers of accumulator per 16
`dpas`, a 4:1 instruction ratio before a single useful operation is chosen.

## 7. Error against the bf16 result

Same real weights, same real activations, same process, compared over all
**71,303,168** fp32 outputs against the control's own output.

| metric | value |
|---|---:|
| max relative error, all outputs | 7.2e6, at one output where the bf16 value is 1.86e-8, a denominator artefact quoted so it cannot hide |
| **max relative error**, outputs above 1% of their row RMS | **26.48** |
| **mean relative error** over those 70,563,326 outputs | **0.0965** |
| max absolute error | 1.095 |
| **global relative L2** | **0.02786** |
| per-row cosine, mean | 0.999579334 |
| **per-row cosine, worst row** | **0.997621824** |
| rows whose largest output moved to another column | **5 of 2048** |
| mean top-8 column overlap per row | 0.9844 |

This is **not** a small error. The project's standing tensor bar is a cosine of
**0.999**, and the worst row of a *single* linear in a *single* layer is
already **0.9976**, before 63 more layers of it. Five of 2048 tokens have a
different largest gate‖up output.

**The error is exactly what the dynamic range predicts, not a bug.** For
symmetric per-token int8, the output's relative error is about
`(max|x| / 440) / rms|x|` (derived from a quantisation step of `max|x|/127`,
uniform noise, divided by the square root of 12). With this chunk's measured
scales that is about 2.8%, and the measurement is 2.79%.

The kernel is separately verified against an **integer-exact CPU oracle** over
a 32 by 32 slice at full K, with a max absolute difference of **0**, so the
arithmetic is the one specified and the error is the quantisation's, not the
kernel's.

## 8. The activation dynamic range

`max|x|` over `median|x|`, per token, over the chunk's 2048 real tokens:

| statistic | value |
|---|---:|
| min | 6.8 |
| **median** | **44.9** |
| p90 | 66.4 |
| p99 | 88.4 |
| **max** | **111.2** |
| per-token int8 scale, min / max | 0.0431 / 0.4311 |

**This is the number that transfers, and it is bad.** A ratio of 44.9 means the
*median* activation lands about `127 / 44.9`, roughly 2.8, quantisation steps
from zero: half of every token's 5120 values are represented by three levels or
fewer. That is a property of this model's post-attention RMSNorm output, not of
this layer or this prompt, so any other linear fed by a normed residual should
be expected to behave the same way.

### Read-through to W4A4, which is out of scope here

The obvious follow-up question is whether 4-bit activations are worth asking
about, since that is the only DPAS shape on this device with a 4x ceiling. The
answer is no, on both halves.

*Error.* int4 activations are 16x coarser than the int8 measured here, on a
distribution whose median already sits under three int8 levels. The 2.79%
relative L2 and the 0.9976 worst-row cosine above are the *optimistic* case.

*Rate* (derived, and conditional on the same rescale). `i4_i4_k64` does halve
the number of group boundaries, one `dpas` per group of 64 instead of two,
which takes the `dpas` share of a group iteration from 256 cycles to 128 while
leaving the 444 non-dpas cycles exactly where they are. That is 572 cycles
instead of 700, a derived **4.45 ms** for this shape, about **1.24x** the
control, and an efficiency against its own 4x ceiling of **22%** rather than
W4A8's 37%. It does not reach 1.53x either, and it needs an int4 activation
quantiser on top. **No W4A4 kernel was written and none is proposed.**

## 9. Dispatch proof

A record had been claimed on this box that week for a kernel that had not run.
The W4A8 arm therefore proves twice, at run time, that it executed the kernel
it claims to have measured:

| check | value |
|---|---|
| module the W4A8 arm opened | `build/kernels/pw4a8.bin` |
| `zeKernelGetName` on the handle the launcher receives | **`pw4a8_gemm`** |
| `zeKernelGetName`, quantiser handle | `pw4a8_quant` |
| `zeKernelGetName`, control GEMM handle | `pf_gemm` |
| `zeKernelGetName`, control dequant handle | `pf_dequant_slab` |
| signature word the executed kernel wrote | **0x57344138**, which is `'W4A8'` |

The first is `zeKernelGetName` on the **same kernel handle** the launcher
receives, not on a name the host looked up separately, and the probe throws if
it is not the expected entry. The second is device-side: the kernel writes
`'W4A8'` into a shared-memory word from one work-item, and the host reads it
back after the arm and throws if it is absent. The control's two handles are
printed beside them so the whole dispatch is visible in one table.

A third, independent check that the *right* kernel ran the *right* arithmetic:

```
the kernel computes the specified arithmetic (integer-exact CPU oracle, 32 x 32 slice)
max |device - host| over the slice: 0
```

The host recomputes 1024 outputs at full K = 5120 from the raw GPTQ nibbles and
the device's own int8 activations and per-token scales, in the same group order
with the same fused multiply-add. It agrees **bit for bit**. A transposed or
mis-packed DPAS operand cannot produce that by accident, so this doubles as the
operand-layout evidence behind the `:s4` and `:b` line in section 5.

## 11. Conclusion

**0.965x of the control measured here, 0.931x of the 5.341 ms bar, against a
1.53x bar.** The gap is not close and no tile, group-handling or tolerance
change was attempted.

- No adoption follows. The W4A8 CPU oracle, the acceptance work, and what
  would happen to the prefill gate, consistency, determinism and backend
  equivalence tests are all unstarted, because the numbers do not reach them.
- No production file was edited and none is proposed.
- The error table and the dynamic range stand on their own as the answer to the
  W4A4 question: do not ask it.

**What this probe does NOT license.** It measured one shape, one layer, one
prompt, one tile (256 by 128 with a 32 by 32 sub-group tile) and one group size,
the checkpoint's 64. It does not rule on: a checkpoint quantised at a larger
group, which is the only change that moves the 4:1 ratio in section 6 and would
need a new checkpoint and its own probe; per-channel or static activation
scales, which change the error question and not the rate one; or any shape
whose N is small enough that the accumulator pressure disappears. Each of those
is a **new** probe with a new break-even.
