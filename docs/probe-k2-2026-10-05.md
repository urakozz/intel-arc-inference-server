**Quantisation** (int4 repo): auto-round 0.16.0, `quant_method` gptq, bits 4, group 64, sym,
`desc_act` false, `dynamic` excludes the 45 `mlp.gate` routers. 16764 int4 linears: every
attention q/k/v/o/gate, every expert (MoE, shared, MoVA) **and the MoVA router `v_router`**.
Plain tensors: embed, lm_head, norms (bf16), `mlp.gate.weight` + `.bias` (**bf16**),
`v_router.bias` (**f16**). Range-fetched on layers 3, 25, 47: `g_idx` sequential (k // 64),
`qzeros` all 0x77777777 (zero point 8); the MoE router weight and bias **bitwise equal** to the
original's; the f16 `v_router.bias` equals the original bf16 bias exactly (as fp32).

**The router biases are large and coarse.** `v_router.bias`: layer 3 22.25..22.62, layer 25
8.19..8.94, layer 47 10.0..10.31; `mlp.gate.bias`: 27.25..27.5, 10.12..10.62, 13.69..14.06. At 27
a bf16 bias has an ulp of 0.125 (layer 3's 100 MoE biases take three values) and the fp32 selection
score `s + b` an ulp of 1.9e-6, so two experts whose bf16 logits are equal (and biases equal) tie
**exactly**, and sigmoid differences below ~2e-6 vanish. Ties at the top-k cut are therefore
plausible on real inputs, not a corner case: the tie rule (lower id) and the dump's gap column
(0 = a tie at the cut) matter for the K2 gate's routing diagnostic. The engine must form the
selection score exactly as `fp32(sigmoid(fp32(bf16 logit))) + fp32(bias)`.

## HF modeling code vs the operator's vLLM fork (`vllm/model_executor/models/k2_horizon.py`)

No semantic disagreement: the router formula, the selection-only bias (`e_score_correction_bias`,
`skip_bias_add=True`, bias kept fp32), x 2.5 after renormalising, MoVA's `SiLU(V_e x)` mix as the
attention V, softplus beta ln 2, the grouped plain-weight norm and the layer kinds are the same.
The differences are rounding and order, and the reference follows the HF code:

1. **Grouped norm, two roundings in vLLM** (:468-499): each group is normalised by `ops.rms_norm`
   with a unit weight (rounded to bf16), then `* self.weight` in bf16 - HF rounds once.
2. **MoE combine** goes through `FusedMoE` (sigmoid + correction bias + renormalise; the scaling
   factor is applied either to the weights or to the combined output, `apply_routed_scale_to_output`),
   summing the 8 slots in the fused kernel, not ascending-id bf16 `index_add_`.
3. **MoVA combine** (`fused_mova_impl` :253-376): GEMM, SiLU, `* w`, then `ops.moe_sum` over the
   4 slots in selection order - HF sums in ascending id with a bf16 rounding per add.
4. **Partial RoPE** is folded into the q/k weight rows for unquantised q/k (`_rope_weight_perm`);
   equivalent, and moot here (full RoPE).
5. Top-k ties: implementation-defined in both.

## Tokenizer and template

- **BOS:** `tokenizer.json`'s `TemplateProcessing` prepends `<|ifm|begin_of_text|>` (0) to every
  encode with special tokens, and `chat_template.jinja` starts with `{{- bos_token }}`. Decision:
  **K2 prompt ids start with 0** (raw-text golden prompts included). `tools/oracle/tokenize.py`
  refuses a tokenizer that adds special tokens; `encode --bos` (added) accepts exactly
  `[bos] + bare ids`. Encoding a rendered chat string *with* special tokens would give two BOS.
- **Chat format:** `<|ifm|im_start|>{role}\n...<|ifm|im_end|>` (250018 / 250019); thinking tags
  `<ifm|think>` (250029/30), `<ifm|think_fast>` (250050/51), `<ifm|think_faster>` (250052/53);
  the generation prompt is `<|ifm|im_start|>assistant\n<ifm|think>\n` (`reasoning_effort` high,
  default; medium -> `think_fast`, low -> `think_faster`).
- **Tool calls (18d):** `tool_call_format` default **`xml`** - not Qwen XML:
  `<ifm|tool_calls>\n<ifm|tool_call>NAME\n<ifm|arg_key>K</ifm|arg_key>\n<ifm|arg_value>V</ifm|arg_value>\n...</ifm|tool_call>\n</ifm|tool_calls>`
  (special tokens 250043/44, 250054-250061); alternatives `json` (`<ifm|tool_call>{"name": ..., "arguments": ...}</ifm|tool_call>`)
  and `xml_typed` (adds `<ifm|arg_type>`). Tool definitions are presented as markdown by default
  (`tool_presentation_format`). Tool results: `<|ifm|im_start|>tool\n...<|ifm|im_end|>`. The fork
  has `tool_parsers/k2_horizon_tool_parser.py` and `reasoning/k2_horizon_reasoning_parser.py`.
- **The two templates differ** (original `a892cd0b…`, 51034 B; int4 repo `60c364d9…`, 51584 B): the
  operator's adds `extract_text` (list content), a "complete set of callable tool names" sentence,
  and accepts assistant history without a thinking field (the original raises).

## The CPU reference (`tools/oracle/k2_ref.py`)

A plain-torch port of the modeling code, one layer at a time (stream.py's `_Prefetch` loads the
next layer's dense tensors; experts are read on first use and dropped with the layer), bf16 or int4
checkpoints (dequant.py's rule, `g_idx`/`qzeros` checked per tensor), dumps in plan 8d's layout
plus the selection gaps. `test_k2_ref.py` (18 tests, ~45 s in `agnes-ref-img` of which ~30 s build the C++ dequant, all pass):

- each §3 trap on its own: plain-w norm (bitwise = `K2HorizonRMSNorm`), the two independent
  groups, the softplus threshold (x = 200 stays 200, the naive formula is inf; the log1p branch for
  20 < x < 28.85), bias for selection only (bitwise = `calc_router_weights`), x 2.5 after
  normalising (weights sum to 2.5), ties to the lower id, ascending-id combine (bf16
  1 + 2^-8 + 2^-8 = 1.0 ascending, 1.0078125 in selection order), the MoVA mix is what the KV
  cache holds (and an unrouted value expert is inert), partial RoPE bitwise = the interleave
  code, GQA h -> h // 4;
- **the port against the vendored HF model on the same tiny random weights: bitwise equal in bf16**
  (every residual and logit; 11-id prompt + 5 cached decode steps; three configs: full RoPE,
  partial RoPE + qk norm, no shared expert / unnormalised MoE) and **bitwise in fp32**;
- the readers: bf16 shards = in-memory weights; an int4 GPTQ checkpoint = its dequantised weights
  (torch and C++ dequant); a permuted `g_idx` refused; stream.attach'd HF = resident HF; the `run`
  / `hfcheck` CLI end to end; the real configs' 16998 names = both real indexes.

One finding on the way: an fp32 matmul rounded to bf16 afterwards is **not** bitwise torch's bf16
GEMM (both accumulate in fp32, in different orders: 109 of 1008 shapes differ by one ulp in 1-4
elements, torch 2.14 CPU), so bf16 mode runs torch's bf16 GEMMs to stay bit-identical to HF.

Measured at real K2 shapes (1 dense + 3 sparse layers, random bf16 weights, real 250624 head; Mac,
16 threads, weights resident): bf16 mode, prompt of 40 ids 1.7 s (55-57 of 100 experts used per
layer), a decode step 0.12-0.17 s; f32 mode 2.0 s / 0.7 s.
