# The golden gate - how correctness is proven

Every kernel test in this repo compares a kernel against a host reference **this
project wrote**. `gemv_test` grades `gemv.cl` against `gemv_ref.h`;
`gdn_step_test` grades `gdn_step.cl` against `gdn_ref.h`. Those tests find
transcription bugs, and they cannot find a shared misunderstanding: a reference
and a kernel written from the same wrong reading of the modeling file agree
perfectly with each other and disagree with the model.

The golden gate closes that hole. It compares the **whole engine** - 774
kernels, the loader, the int4 repack, the captured command list, the decode loop
- against a reference the project did not write: `transformers` on CPU, the
pure-torch gated delta rule, `attn_implementation="eager"`, over the same
checkpoint dequantised by the same convention the C++ loader is bit-compared
against (`tools/oracle/README.md`).

## Where it stands

> **3 prompts x 32 greedy tokens. 93 of 93 determined rows element-exact
> against the CPU oracle, 3 undetermined rows all inside the oracle's own argmax
> set.**

The prompts are 42, 61 and 38 ids of English prose, Python source and Chinese
text with a trailing emoji variation selector. Their ids are committed
(`tests/golden/prompts/{prose,code,cjk}.ids`); the roughly 1 GB of golden
`.safetensors` are not, and are regenerated by `tools/oracle/golden.sh`.

`prefill_gate_test` runs the same comparison through one `Engine::prefill` per
prompt instead of one replay per id, against the same oracle, and reaches the
same tally.

## What the gate asserts, and what merely diagnoses

| | Bar | Measured |
|---|---|---|
| generated ids against the golden `tokens`, per prompt | **the gate, and the only thing that fails the test** | 93/93 determined rows exact, 3 undetermined and all in the golden argmax set |
| GDN state after the prompt, per layer, cosine | diagnostic, marked `**LOW**` below 0.999 | 0.999912369 (prose), 0.999712545 (code), 0.999901750 (cjk); 0 of 144 layer-prompt pairs below the bar |
| per-layer residual tap cosine | diagnostic, marked `**LOW**` below 0.999 | a run of low rows on `code`, down to about 0.989 at layers 52 to 57 |
| logits row at every decision point, cosine | diagnostic | above 0.9998 across all rows |

**Token equality is the gate. Every cosine in this document is a diagnostic**:
they mark rows `**LOW**` and they do not fail the run.

That is not laziness, it is the only arrangement that survives contact with 64
layers of bf16 residual drift. A hard tensor bound is either useless or flaky,
and the `code` prompt below is the demonstration. The GDN state cosine was
originally specified as a hard bound and was demoted to a diagnostic before it
ever shipped: the margin at the time was 5.4e-4, so the bound would have been
one legitimate numerics change, or one longer prompt, away from failing the gate
on a recurrent-state cosine while every token id was exact.

### Undetermined rows: the rule, and why it is not a weakening

**A golden decision row whose top-1 is not unique is UNDETERMINED.** On such a
row the gate requires the engine's id to be a **member of the golden argmax
set**. On every other row it asserts element equality at full strictness, and
every such row must pass.

This exists because the oracle's logits are **on the bf16 grid**. The dump
records `out.logits[0].to(torch.float32)` and `out.logits` from a bf16 model is
bf16, so widening lands exactly on bf16-representable values: every word in
every golden `logits` tensor has zero low 16 bits. The reference therefore
carries about 8 mantissa bits at the decision and **cannot resolve two
candidates that fall inside one ulp of each other.**

It was found the way these things are found. One checkpoint's `prose` prompt
diverged at generated step 15 and never recovered, which is what a greedy
sequence does after one different token - 15 of 32 is one event, not seventeen.
The oracle's top two logits at that row were **bit-identical**:

```
decision row for generated step 15
   id    271  f32 19.750000000  bits 0x419E0000
   id    353  f32 19.750000000  bits 0x419E0000
   top-2 gap = 0.000000000e+00   bf16 ulp at that magnitude = 1.250000000e-01
```

The engine's fp32 logits separated the same pair by 0.0156, about one eighth of
one bf16 ulp, in favour of 353. `torch.argmax` broke the exact tie by lowest
index and returned 271. Grading the engine on `torch.argmax`'s tie-break was
never something this gate set out to do, and nobody noticed it was doing it
until a coin came up tails.

The rule is **not a tolerance**. It declines to assert an answer the reference
does not contain, and nothing else. It applies retroactively and symmetrically:
earlier gate runs that reported a clean sweep are re-read with their tied rows
marked undetermined, and not one determined row moved when they were.

`tests/golden/golden_gate_test.cc` computes the full argmax set from the golden
`logits` row at every decision, so the tie census is **committed code deriving
the fact** rather than a number pasted from a console. One standing example: on
the `cjk` prompt the decode path emits token 4960 at generated position 22 where
the oracle emits 271, the oracle's own logits mark that row undetermined because
4960 is in its argmax set, and the prefill path takes 271 at the same row. That
is a sub-ulp tie between two independently rounded paths, confirmed by the
oracle rather than argued.

Across three checkpoints the ties clustered onto a **different prompt each
time** - two on `cjk`, three on `prose`, two on `code`, none elsewhere - which
is consistent with the mechanism being an arithmetic accident of the bf16 grid
at one particular decision rather than a property of a prompt, a checkpoint or
the engine. Do not over-read the clustering: it is a pattern noticed after
looking, over seven events, with a plausible innocent explanation (a prompt's
logit magnitudes set the local bf16 ulp) and no mechanism proposed or tested.

### Teacher-forcing, and one statement that has to be in the right place

After a divergence the gate continues **teacher-forced**, so the tail is still
judged against the reference's own context rather than against a sequence that
has already left it.

**The flag must be set before the advance, not after**, and that ordering is the
whole point. The replay at the divergence row is the one that writes the
diverging token into the KV cache, the conv ring and the GDN recurrent state, so
letting it consume the engine's own id and only forcing from the *next* row
leaves every later row reading a contaminated state. Measured both ways on the
same prompt:

| flag set | teacher-forced rows' logit cosine | determined rows exact |
|---|---|---|
| after the advance | 0.628 … 0.998 | 26/29 |
| **before the advance** | **0.9999** | **29/29** |

Same code, one statement moved. The cosine band is the evidence that the tail is
genuinely on the reference's context: 0.63 is what a diverged sequence looks
like and 0.9999 is what every other row in this document looks like.

## How the tap is compared, and why it is not a layer output

The engine's per-layer tap is **not** layer *i*'s output. The copy runs after
layer *i*'s last kernel, and the residual stream is advanced only by the
residual-fold kernel, so `tap[i]` holds the hidden state with layer *i*'s
**mixer** folded in and layer *i*'s MLP still sitting un-folded in the partials
buffer, where layer *i+1*'s leading fold will pick it up. The oracle's
`resid.L{i}` is the layer *output*, post-MLP. Comparing the two directly would
report a divergence that is a definition mismatch and nothing else.

The comparator is therefore **built** from two golden tensors rather than read
from one:

```
expected_tap[i][t] = bf16( resid.L{i-1}[t] + mixer.L{i}[t] )     i >= 1
expected_tap[0][t] = bf16( embed[ids[t]]   + mixer.L0[t]   )
```

summed in fp32 from the two golden bf16 tensors and rounded round-to-nearest-
even, because that is the arithmetic the fold kernel does. The oracle dumps no
embedding tensor, so layer 0's predecessor is gathered host-side out of the same
bf16 table the device gathers from, contributing no error of its own.

**Layer 63's post-MLP residual has no tap** and none is invented. It is covered
twice over instead: the residual buffer after the fence *is* that vector, so the
test compares it against golden `resid.L63` directly, and the logits and the
token ids cover it again.

## The two named divergence classes

Both were named in advance as expected, and both were measured.

### 1. GEMV accumulation order and the dequantisation rounding point

The engine never materialises a weight: it computes `scale · Σ(q − 8)·x` with
the products and the sum in fp32 and the scale applied once per group of 64. The
oracle materialises `bf16(scale · (q − 8))` and lets torch multiply bf16 weights
by activations. Two different accumulation orders, two different rounding
points, on identical bits - and **the engine is the more accurate of the two**.
The analytic cost of the oracle's extra per-weight cast to bf16 is about 0.2%
RMS per weight (an 8-bit mantissa gives a relative rounding error of about 2⁻⁹);
that figure is estimated, not measured.

What is measured is the effect on an actual activation. The embedding gather is
an exact bf16 row copy, so **every** bit of the layer-0 tap error is layer 0's
mixer, and it measures **0.45% to 0.68% max relative on one mixer output** -
the same order as the estimate. An accumulation of a few thousand weight-level
errors of that size into one dot product, then through a norm and a second GEMV,
landing at half a percent, is what "expected class" means here.

### 2. The softmax path

The oracle runs an fp32 softmax over the whole row. The engine runs a blocked
flash-decode with per-block running max and sum merged by a reduction kernel.
The `exp` implementations differ and the merge order differs from a single-pass
softmax, so this class was expected to show up as full-attention layers being
systematically worse than GDN layers.

**It does not.** Comparing the mean of per-layer median cosines, the gap between
the 48 GDN layers and the 16 FA layers is about **2e-6** on every prompt: two
parts per million, three orders of magnitude below the diagnostic bar. The
softmax path contributes no measurable divergence of its own at these depths,
and class 1 is the whole story.

### A third thing that could have diverged, and did not

`lm_head` is `[5120][248320]` for tiling, but only 248077 of those columns are
real tokenizer ids; the argmax kernel masks the 243-column tail to `-INFINITY`
while the oracle argmaxes the full width. If a padding column had ever won a row
the two would have disagreed by construction. The test reports the golden argmax
both masked and unmasked at every decision row, and they have been equal on
every row measured.

## The `code` prompt's low rows - the result that justifies the design

The `code` prompt is the only one with tap cosines below the diagnostic bar, and
the shape of the failure is worth the space.

A small number of the (layer, position) tap comparisons fall below 0.999, and
they sit on **three positions out of 61**. Every layer's *median* over positions
is about 0.99994, layer 63 included; the minima and the medians differ by three
orders of magnitude in the error. The other two prompts have none at all.

At its worst, one position reads a tap cosine of 0.9863. Two facts kill the two
cheap explanations:

- **It is not a small denominator.** The oracle's magnitude at that point is
  275.7, dead centre of that layer's distribution over positions (189 to 408).
  The absolute error there is 58.8 against a typical 3: a 20x outlier in
  absolute terms, not a normalisation artefact.
- **It is not one layer and it is not one kernel.** The per-layer error at that
  position grows monotonically and smoothly with depth - 0.007 at L0, 0.407 at
  L20, 1.017 at L40, 4.875 at L50, 33.1 at L55, 58.8 at L59 - and then
  *recovers* in relative terms by L63. There is no step change at any single
  layer and none at any layer *kind*. A kernel defect would put the step
  somewhere.

What it is: **one token position whose residual direction the network amplifies
strongly**, applied to the class-1 seed that every position carries. The test
prints the attribution that shows it, comparing each layer's own contribution on
both sides. At that position the contribution cosine sags to 0.982 at L55 and
0.896 at L60 while the accumulated tap is still at 0.99, and L60's contribution
then *pulls the tap back up*. A layer whose output is a strong function of the
residual direction, with both engine and oracle falling into the same attractor.
That is high local gain, not a bug.

Three independent facts say the amplification is harmless where it matters: the
prompt's GDN state cosines stay above the bar, the neighbouring positions are
all back at about 0.9999 so it does not propagate along the sequence, and **all
32 of its generated ids are exact.**

**This is why the gate is token equality.** A hard 0.999 tensor bound would have
failed this run, on a prompt where the engine reproduces the oracle's output
perfectly. Tokens gate; tensors diagnose.

## Determinism

The gate has been run many times across many builds of the test binary, and
every quantity two logs have in common agrees to all nine printed digits. The
diagnostics only ever grew as they were added; they never moved.

That is `replay_determinism_test`'s property observed end to end on the real
checkpoint: 774 kernels and 19 modules captured, 8 tokens by 3 runs bitwise
identical from reset, on the token ids, on a per-layer residual tap and on every
persistent buffer, then once more from a re-zeroed state.

`prefill_replay_test` does the same for the prefill walk: the exact bytes of the
GDN state, the convolution ring, both KV caches, the control block and the
logits, across two full chunks plus a ragged tail.

And `prefill_backend_equivalence_test` holds the Level Zero and sycl-tla prefill
paths **bitwise equal** - 0 words differing and 0 sign-of-zero differences on
all five case families - so the backend selection cannot change a result.

## The third implementation

The trust chain has a ceiling that the gate alone cannot lift. The C++ loader
and the oracle are pinned to the **same** dequantisation convention,
bit-exactly, by `dequant_fixture_test`. So a convention that is wrong about how
the checkpoint's author packed the nibbles would move the engine and the oracle
**together**, and the gate would still pass.

Closing that needs a third implementation that shares nothing with either.
`tools/oracle/vllm_check.py` is it: it hands the three committed `.ids` files to
an offline `vllm.LLM` as `prompt_token_ids`, so **no tokenizer is in the loop**
on either side and a tokenizer difference cannot masquerade as a token
difference. It reads the oracle's `tokens` tensor straight out of the golden
`.safetensors` rather than a derived copy, and exits 0 only if every id matched.

**Result: 96 of 96 ids equal across the three prompts.** All three agree.

Two settings make the check mean what it says.
`SamplingParams(temperature=0, max_tokens=32, min_tokens=32, ignore_eos=True)`,
because the oracle's greedy loop is a bare argmax with no stop condition and
without `ignore_eos` a stop would silently shorten the comparison; and prefix
caching off with `max_num_seqs=1`, because a correctness check has no business
letting a cached prefix or a two-prompt batch change which kernel shape runs.

**Why this is a third implementation and not a second look at the same code.**
Read off the run's own log: the int4 weights go through vLLM's own GPTQ unpack,
the GDN layers run Triton kernels, the full-attention layers run FlashAttention,
and all of it runs on the GPU against the oracle's CPU and the engine's own
Level Zero kernels. Different unpack, different kernels, different device,
different scheduler. The only thing all three share is the checkpoint's bytes
and the prompt ids. That is what makes 96/96 informative: the packing
convention - zero point `q − 8` with no `qzeros` stream, group 64 along `K`,
`[K/8, N]` u32 words, `desc_act: false` - is being read the same way by an
implementation that never saw our dequantiser.

A control run with `--enforce-eager` takes a different execution path through
the same weights and produced byte-identical id blocks, so the verdict does not
rest on the compiled path.

Two caveats worth keeping. **This closes the chain for these prompts**, which is
a check with a recorded result rather than a regression test, and it should be
re-run after any change to the dequantisation convention or the loader's packing
assumptions. And **a self-quantised checkpoint with an int4 `lm_head` cannot go
through this route at all**: vLLM picks its backend from `quant_method` and
routes such a checkpoint to a post-load path that fails before generating.
Whether the packed head is the cause is a plausible reading of the source and
**not** a measurement - the traceback never names the failing module. That link
of those artifacts' trust chain is open and stays open.

## A green gate is not evidence unless the run says which kernel it dispatched

This is the most expensive lesson in this document.

A record was once claimed for a delta net scan kernel that had passed its gates.
It had not run. The selector resolved, the gates ran, everything was green, and
the kernel the run actually launched was the old one.

Every gate run now prints the entry it launched, read back from the pointer the
launcher handed the kernel cache, and the non-band tests assert that the printed
entry matches the selector's resolution:

```
gdn scan selector: B70_PREFILL_GDN_SCAN=dpas_split -> entry pf_gdn_scan_dpas_split
gdn scan entry LAUNCHED: pf_gdn_scan_dpas_split
```

Run with its dispatch proven, that same kernel **failed**: 92 of 93 rows, with
one state cosine at 0.996. The cause was one operand of one term, and the fix
took it to 93/93. The whole episode is in
[prefill-gdn-scan-split-fix-2026-09-23.md](prefill-gdn-scan-split-fix-2026-09-23.md).

The probes in this repo carry the same rule. The W4A8 probe proves dispatch
twice: once by asking the driver the name of the kernel handle the launcher
received, and once by having the kernel write a signature word from the device.

## One approximation, declared

The delta net scan runs approximate split-BF16 arithmetic and is gated on tokens
and state cosines rather than on `memcmp`. **It is the only default in the
prefill path that is not bit-identical to what it replaced**, and it is worth
2.33x on its own profile row.

Every other kernel that replaced another is compared **bitwise**, not by
tolerance.

The scan's honest limit: one operand inside its A2 term is still a single BF16
value, measured harmless on three prompts of one checkpoint and not proven in
general.

## Running the gate

```bash
tools/box.sh test golden_gate_test          # sync + build + ctest
# or, for the full diagnostic log:
tools/box.sh run './build/tests/golden_gate_test "$PWD/<golden-dir>" "$PWD/tests/golden/prompts" <snapshot>'
```

**A golden set belongs to exactly one checkpoint**, and to the container image
that produced it, since the oracle is `transformers` running inside that image.
`ctest` registers one golden directory; other sets are invoked by hand with the
directory, the prompt directory and the snapshot as arguments.

Absent goldens make the test exit 77, which ctest reports as **SKIP**. The test
also asserts that each `.ids` file has as many ids as its golden file's first
residual tensor has rows, so a stale ids file cannot silently pass.

**Measured cost**: about 24 s standalone, of which 13.4 s is the checkpoint
load, at a peak RSS of 19.5 GiB with a bf16 head. One checkpoint load serves all
three prompts. Regenerating a golden set costs 18 min 16 s for all three prompts
on an idle machine, and 28% longer under a 12-core compile - the CPU oracle is
the one thing in this project that genuinely contends for the host.

Suite total: **86 tests**, all passing.
