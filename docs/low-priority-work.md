| **TP + slots: several requests at once on the two-card tensor-parallel engine** (ruled out 2026-11-11, operator; branch `tp-slots`, Codex's build plus the fix agent's WIP) | One TP engine with sequence slots (one prefix cache, every slot's KV on both cards). One slot is token-identical to main's TP; several at once lose to replica: aggregate t/s at 1 / 2 / 4 requests, bf16, MTP: TP + slots 108 / 116 / 121, replica + slots 72 / 137 / 206 (rough, beside CPU jobs). Found broken: MTP at 2-4 requests fails with crossing errors ("flag came without its data's trailer"); spec off rejects one batched id by 100 ulp (a row-path error, not rounding); the crossing kernels alone pass 5000 replays at M = 1..8, so the fault is in the engine's row path | Batched MTP drafts across slots (today one slot at a time, which is why it does not scale), the row-path fault found with `tp_slots_rows_test` (batched vs lone logits, M = 2..8), then the f32-judged card checks. Only worth it if replica's separate prefix caches prove costly in real opencode sessions |
| **A shared paged KV pool instead of fixed slots** (considered and postponed 2026-11-11, operator) | vLLM-style: one pool of small KV blocks shared by all requests; any request may grow to `--max-len` while the others stay small, so several medium sessions fit where fixed slots cannot (e.g. 3 x 60k beside each other). Postponed because the engine optimises one or two users' local agentic sessions with guaranteed top performance: fixed slots reserve the main session's context, never preempt, and need no shared-pool bookkeeping (block allocation races, memory fences between requests, recompute on eviction) | Block tables in the decode / verify / prefill attention kernels (paged KV reads), a block allocator in the scheduler, a preemption policy (recompute vs swap to host) and its latency limits; the f32-judged slot tests rerun. Worth it only if real use shows many concurrent medium-length sessions |
| **An int4 output head with GPTQ-calibrated codes** (2026-11-11, operator) | The output head (248,320 x 5120, 2.5 GB bf16 in the checkpoint) runs as int8 per row today, about 8 % of the bytes a decode step reads; int4 would save about 4 % of every step, but plain rounding to int4 costs accuracy. A vLLM fork cut the int4 head's error by 18.9 % with offline GPTQ codes, and by another 14 % keeping the ~8k most frequent tokens' rows exact (+0.7 % decode) | Quantise only the head, offline: GPTQ (or AutoRound) over hidden states dumped from calibration prompts, from the bf16 head already in our checkpoint; a loader path for int4 head codes; the int4 decode GEMV for the head; judged by the f32 judge and MTP acceptance |
| **A faster full-chunk prefill attention at long depth** (2026-11-12, operator) | Deep in a session a full 2048-token chunk slows with the history: 934 ms at 4k, 1,223 at 32k, 2,214 at 128k (int8 prompt pass, one card). At ~72 % of peak prefill would be ~+10 % at 32k and ~+30 % at 128k (derived; nothing changes below 16k). Felt when a large tool output lands deep in a long session; short turns already use split-K | A flash-attention kernel for long KV at full chunk width (tiling, KV reads, DPAS scheduling), the same output under the f32 judge, timed at depth 32k / 128k one card and TP |

The workaround: the l0 prefill or the bf16 cache | Read the chunk's own new rows from bf16 inside the chunk (they are computed in bf16 anyway), older rows from int8 - no extra memory. Closes when the tool-call test has no invalid call under l0-int8 + int8 KV, judged against the f32 reference.
