# Box validation queue

Work merged into `main` without running on the card, in the order to validate it when the box is
back. Each entry names its checklist or its tests. Remove an entry when it has passed on the box.

## How to run

The rows below are a runbook, `tools/box_validate.sh` (stages: `tools/box_validate/stages.sh`).
From the Mac, in the checkout to validate (main), with `tools/box.env` set:

```sh
tools/box_validate.sh --dry-run      # every command it will send and run - no ssh; read it first
tools/box_validate.sh                # sync, build, run every default stage, wait, summarise
```

- **One detached run on the box.** The script syncs the tree to `~/b70-inference-server-validate`,
  extracts the G0 baseline (default `b32aaaf`, main before the first blind code commit) into
  `~/b70-inference-server-g0-<sha>`, and starts `tools/box_validate/remote.sh` through
  `tools/probe/detach.sh`. The run survives a dropped ssh session or a closed laptop; the Mac only
  polls. Every GPU stage holds `~/b70-gpu.lock`, builds use `-j44`, and timed stages run
  interleaved rounds after a warm-up (median of 3, `uptime` and the idle grade recorded).
- **G0 first, stop the line.** `g0.build`, `g0.sha` (sha256 of every kernel binary present in both
  builds), `g0.bitwise` (the golden / prefill / replay gates on both builds, output compared line
  for line with timings dropped) and `g0.suite` (the baseline's whole suite on the new build). Until
  all four pass, every later stage is recorded SKIP "blocked"; `--force` runs past it.
- **Resumable.** Results live in `~/b70-validate/<tree>/<sha>-vs-<baseline>/`: per stage a
  `<id>.status` line (PASS / FAIL / SKIP, reason), `<id>.log`, JUnit files. Re-running the same
  command re-attaches to a live run or resumes a finished one, skipping stages already PASS;
  `--redo <id|row>` runs them again, `--only r11` runs one row, `--status` looks without
  touching anything, `--summary` fetches and writes the summary only.
- **The summary** is `box-validation-<date>.md` in the repo root: a table per row (result, reason,
  log path), the numbers each row asks for, what no stage can run (with the reason), and the
  commands of the opt-in and manual stages.
- **Server rows** (r2.auto_rows, r12.a4, r16.serve's tool-call set, opt-in r8.auto_rows and
  r16.mtp_rows) run one `b70-serve` per arm and
  round (`tools/box_validate/serve_run.sh`, rounds rotated, `R2_ROUNDS` = 3) and drive it with
  `tools/box_validate/serve_client.py` (stdlib): the golden prompts as completions and the A4 set
  as chat requests with their tools, greedy, `return_token_ids`; per request the output ids and
  text, usage, wall time and the decode-only t/s from the server's own `--log-requests` record.
  `serve_client.py compare` is the greedy-identity check between arms, `table` the medians and
  geomean ratios. b70-serve's usage carries no accepted-draft count yet, so acceptance comes from
  `mtp_gpu_test --bench` and `b70-decode --ids --mtp` instead.
- **Long-context MTP** (row 6): `mtp_verify_{32k,128k}_test` and `mtp_gpu_{32k,128k}_test` (label
  `longctx`) exit 77 at once unless `B70_LONGCTX_TESTS=1`, so a plain `ctest` costs what it did;
  r6.mtp_long sets it. `b70-decode --ids ... --mtp K|auto` (greedy) is r6.greedy_long's and the
  120k passkey's path without the server.
- **Not run by default:** long hand runs and anything needing operator input are opt-in
  (`--with r11.passkey120k,r11.passkey262k,r7.passkey`, `--with optin` for all) or manual (their
  commands are printed in `--dry-run --with ...` and in the summary): passkey at 120k (int8 KV and
  with `--mtp auto`) / 262k / 95% of auto, decode at auto depth, A12's 32k / 64k rows, A4 runs that
  need a reference dir, the draft-vocab server rows, llama-benchy and vLLM rows, the opencode
  replay, Ornith's P0 profile, sweeps and prefill speed, K2's reference run (r14.oracle), decode
  speed and sweeps, K2's prefill P0 and speed (r15.p0, r15.speed: flash against `B70_K2_ATTN=eager`
  pairs) and the eager golden prefill gates (r15.golden_eager, for when r15.golden fails
  determined rows), Ornith's MTP server rows, passkey at 120k / 250k and llama-benchy rows
  (r16.mtp_rows, r16.passkey, r16.benchy), and Ornith's A4 (manual r16.a4: it needs an Ornith
  tool-call set first). Stages whose data is missing (Agnes checkpoint, the Ornith checkpoint and
  golden sets from 15a - `oracle-out-ornith`, `oracle-out-ornith-mtp` -, the K2 checkpoint
  `SNAP_K2` and `oracle-out-k2`) are SKIP with the missing key; `--push-data` copies the Agnes
  checkpoint, `oracle-out-agnes*` and `oracle-out-ornith*` (made on the Mac from the int4
  checkpoint, plan 15a Task 0) from this Mac first, and `--with r14.oracle` makes
  `oracle-out-k2` on the box CPU (18a's `k2_ref.py` on the int4 checkpoint, ~20 min, resumable;
  the K2 gates on decode and prefill then run in the same launch).
- **Kernel binaries by name** (`kbins`): r10.r0, r13.r0 and r16.r0 check that the binaries Ornith's
  lists bind are in the build - since row 19 (the real checkpoint, spec 15 §13) its greedy argmax
  is Qwen3.8's `argmax_stage1_M{1..4}` (its `tokenizer.json` defines 248077 ids) and its a||b the
  int4 `gemv_M{1..4}_K2048_N128_S1_L1` - and say which of them G0 listed as added.
- **Run directly, not through ctest:** `golden_server_test` and `prefix_gpu_test` against Ornith
  (r16.golden_server, r16.prefix - not registered for Ornith, as they would fail rather than SKIP
  without the checkpoint; the runbook's `needs` SKIPs them instead).

**Adding a row** (a branch merged blind): add it to the table below **and** a `row N` block of
stages to `tools/box_validate/stages.sh` (the header there says how; `--dry-run --only rN` shows
it, `python3 tools/box_validate/test_box_validate.py` checks the registry). Remove both when the row
has passed.
