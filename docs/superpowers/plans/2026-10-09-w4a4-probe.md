## Why group 256 (derived from the W4A8 measurements)

A GEMM over depth K costs K/16 bf16 DPAS, or K/64 int4 x int4 DPAS plus K/g rescales (one per group
along K - a rescale is needed wherever either operand's scale changes, so the group is the coarser
constraint of the two). Fitting the four measured W4A8 points (g64 0.97x, g128 1.22x, g256 1.43x,
per-channel 1.75x against bf16) gives a rescale of **~1.6 DPAS issues** and **~0.875 of peak**
(each point within 3 %). For int4 x int4 the same fit projects (derived, unmeasured):

| g | 64 | 128 | **256** | 512 | 1024 | per-channel |
|---|---:|---:|---:|---:|---:|---:|
| x bf16 | 1.35 | 1.9 | **2.5** | 2.9 | 3.2 | 3.5 |

Today's h8 int8 path is per-channel: ~1.75x ceiling (1.35-1.52x per linear measured, 1.28x whole
prefill). **g256 is ~1.4x over it** while keeping weight groups fine enough to hope for accuracy.

**For int8 the answer is the opposite: per-channel stays best.** int8 is fine-grained enough that
groups buy little accuracy, and W4A8's measured speeds fall with finer groups (g64 0.97x, g256 1.43x,
per-channel 1.75x). h8 (per-channel int8, rotated) remains the int8 default; this probe does not touch it.

## Global Constraints

- Probe-first: no engine kernel, no new checkpoint format in the tree. A g256 weight-only checkpoint
  would be a second format beside int4 g64 (the operator's one-format rule): it is justified only if
  this probe shows W4A4 prefill is worth it AND g256 weights keep decode quality near g64's - both
  recorded, then the operator rules.
- Accuracy is measured on the same prompts and metrics as h8's acceptance (probe-w4a8 §15.4-15.5),
  so the numbers sit in one table.
- CPU work runs in the oracle container (`tools/oracle/run_in_container.sh` on the box, the
  `agnes-ref-img` image on the Mac); the bf16 Qwen3.8 is 54 GB - on the box CPU (queue row 35) unless
  the operator re-downloads it to the Mac.
- Signed commits on branch `w4a4-probe` from main; no merge, no push; no `rm -rf`; never read or commit
  `tools/box.env`.

## Review Focus

1. **Both operands at g256, aligned:** the activation groups and the weight groups must cover the same
   K ranges (0..255, 256..511, ...), after the rotation, or the simulated cost model is not the
   kernel's. A test pins the alignment.
2. **The rotation is h8's exactly** (`tools/rotate/rotation.py`'s 1024-block Hadamard, both sides), so
   the only new error is the int4 grid.
3. **Symmetric int4 grid:** q in [-8, 7], scale = max|v| / 7.5 per group (the RTN rule `rtn` already
   uses), fp32 accumulation; the power-of-two variant rounds each scale up to 2^ceil(log2 s) (MX-style
   shared exponent), which can only enlarge |error| - a test checks it is never smaller than the fp32
   scale's.
4. **The controls run in the same load:** `none`, `h8` (today's default) and the checkpoint as shipped
   (W4A16), so W4A4's number is read against h8's on identical prompts.
5. **Down / o_proj / out_proj** (the linears whose inputs only the runtime rotation can rotate) are
   reported separately per linear class, as probe-w4a8 §14.2 did - an end-to-end pass can hide one bad
   class.

**As built (2026-10-10).** `h4` = `fake4(R.rot(x, d)) @ fake4(R.rot(W, d))^T` in fp32 with h8's signs
`d = R.signs(K, R.SEED + K)`; `fake4` = q * s, q = clamp(round(v / s), -8, 7), s = max|v| / 7.5 per row per
`--group` along K (offsets 0, g, 2g, ... on both operands; an all-zero group s = 1). `h4p2` rounds s up to
a power of two exactly (frexp, not log2). W is the gate checkpoint's dequantised g64 weight, as for h8 (so
`h4` re-rounds the g64 grid's values onto g256 after the rotation - RTN, the "understates a tuned g256
checkpoint" caveat of Task 2 Step 2). `w4a16` is the module's own bf16 forward (bitwise the `logits`
mode). "Per linear class" is two things: in every full pass each replaced linear's own error against
x W^T on its input (rel L2, worst-row cosine), summarised for attn_qkv / attn_o / gdn_in / gdn_out /
gate_up / down; and `--per-class V,...`, one end-to-end pass per class with V on that class only (the rest
`none`) - argmax / top-5 / KL need logits. The KL is KL(p_bf16 || p_variant) at T 1 over ids
< `--vocab-used` (248077 on the box). rel L2 / worst cos / argmax / top-5 stay CR.compare's (full width),
so §15.4's columns read the same. A K the group does not tile is refused before any forward, by name.
