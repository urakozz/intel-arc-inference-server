# Spec 1.5 - Decode performance: close the measured gap

Status: approved design, 2026-08-25. Follows spec 1
(`2026-08-22-phase0-decode-core-design.md`), which closed with a correct,
deterministic engine at **23.73 t/s** against vLLM's **31.50 t/s** (both
measured, tg256 @ depth 4096 - docs/BENCHMARKS.md). This spec is the
performance pass. It changes no external behaviour: same CLI, same model,
same correctness bar.

## 1. Where we stand (all measured 2026-08-25 unless labelled)

Step time 42.141 ms/token, partitioned (docs/12 top table, docs/05 §phase-1):

| bucket | ms | provenance |
|---|---|---|
| int4 + bf16 GEMV family, 257 launches | 28.346 | per-kernel **probe transplant - a floor, not an in-situ charge** (docs/12 `gemv` → Measured) |
| attention block work (decode+reduce live blocks) | 2.314 | **estimated** (two-point depth extrapolation, ±0.2 ms; floor 2.144 measured) |
| attention early-out + embed_gather + argmax | 0.054 | measured |
| host outside the fence | 0.097 | measured |
| **unsplit bucket: 369 launches** - `prep` 241, `gdn_step` 48, `attn_prep`/`attn_reduce` 32, `a‖b` GEMV 48 | **11.330** | derived remainder; avg 30.7 µs/launch |

Target: 31.746 ms/token (= vLLM's 31.50 t/s). Gap to find: **10.395 ms**.
Roofline: 37.97 t/s (15.540 GB/token ÷ 590 GB/s, both measured).

**The honest arithmetic the whole spec hangs on.** If GEMV really sits at its
floor, then even a *perfectly* eliminated bucket leaves
28.346 + 2.314 + 0.151 = 30.811 ms → 32.5 t/s, and beating vLLM requires the
bucket to shrink from 11.330 to below **0.935 ms**. The bucket's own lower
bound is not zero: its true memory traffic is worth roughly 0.7-1 ms at full
bandwidth (estimated - docs/12 `prep` → Measured derives ~0.67 ms for the
prep family alone at 590 GB/s) plus ~0.19 ms of dispatch (369 × 0.52 µs,
measured probe_replay). So the win is *arithmetically* reachable but tight,
and it has a second path: the in-situ profiler (§3) may show GEMV **above**
its floor, in which case GEMV tuning (lever 4) reopens budget the bucket
doesn't have to supply. Both paths are in scope; the profiler decides the
split. This paragraph is the calibration for the §6 gate - nobody should be
surprised there.

## 2. Success bar and stopping rule (ruled 2026-08-25)

- **Success:** tg256 @ depth 4096 median-of-3 ≥ 31.50 t/s with the full suite
  green and the golden gate exact. Recorded, spec closes.
- **Stopping rule:** work the lever ladder (§5) in profiler-ranked order.
  When the levers are exhausted - or the profile shows the remaining levers
  cannot reach the target - run the §6 gate. If short: **stop and write the
  re-assessment memo**; redesigns (fusion, SLM-staged attention, layout
  changes, bucketed lists) enter only by explicit user decision on that memo.
  No silent scope extension.
- **Correctness bar (hard, ruled):** every accepted change keeps the golden
  gate at **96/96 tokens element-exact** vs the oracle and the suite green.
  A change that flips any golden token is *stopped and surfaced as a
  decision*, never silently accepted - regardless of its speed. (Plan-3
  evidence says the slack is large: a 21% hidden-state deviation left tokens
  exact - docs/14. Most retunes are expected to pass.)
- Determinism discipline is never relaxed: no fp atomics, fixed grids and
  reduction orders, byte-identical replay. Any restructured kernel re-proves
  its reference comparison under the established regime (bit-exact where the
  family is bit-exact today; the Task-5 bf16-ulp bar where it is not).

## 3. Stage 0a - the step profiler (the instrument)

**Why first:** the 11.330 ms bucket and the 28.346 ms GEMV floor are
definitionally coupled - one derived the other. Whole-step deltas cannot
attribute a 0.3 ms change to a lever. One instrumented run replaces both
with in-situ per-kernel numbers.

### 3.1 `l0::EventPool` / `l0::Event` (new, `src/l0/event.{h,cc}`)

RAII wrappers in the house style (mirror `Fence`): pool created with
`ZE_EVENT_POOL_FLAG_HOST_VISIBLE | ZE_EVENT_POOL_FLAG_KERNEL_TIMESTAMP` and a
caller-given capacity; `Event(pool, index)`; `Event::kernel_timestamp()`
returns the device-clock `{start, end}` of the *global* timestamp pair from
`zeEventQueryKernelTimestamp`; `Event::reset()` (`zeEventHostReset`).
Duration math lives in one host helper: cycles → ns via
`ze_device_properties_t::timerResolution`, with wraparound handled by masking
to `kernelTimestampValidBits` before subtracting - durations only, never
absolute times across the step.

### 3.2 `CmdList::launch` signal parameter

`launch(Kernel&, gx, gy = 1, gz = 1, Event* signal = nullptr)` - passes the
event handle as `hSignalEvent` of `zeCommandListAppendLaunchKernel`. Default
null; every existing call site compiles unchanged.

### 3.3 Profile mode in `runtime::build`

Same pattern as the residual tap: `build(ctx, m, b, tap, ProfileEvents*)`
where `ProfileEvents` (caller-owned) holds the pool and one event per launch.
When non-null, launch *i* signals event *i*. `CapturedStep` additionally
carries `labels` - one string per launch, `"L<layer> <kernel> <variant>"`,
filled from the walk (the walk is deterministic, so index → site is exact);
labels are host-side and always filled (645 small strings, no cost).

**Profile mode is never bench mode.** Recorded bench rows always come from an
event-free list; the profiler prices *shares and per-kernel deltas*, the
bench prices the *absolute step*. Both facts get stated wherever profiler
numbers are recorded.

### 3.4 CLI surface

`b70-decode <model> --profile [--depth N] [--steps K]` (defaults 4096 / 32):
ingest to depth (un-instrumented list), then replay K instrumented steps,
averaging per launch. Output: per-launch table (site, µs, share), rollups per
kernel family and per layer kind, and the two totals - Σ durations vs fence
wall - whose difference is the measured dispatch/gap cost (expected ≈0.34 ms,
estimated from probe_replay's 0.52 µs × 645). `debug_resid` off.

### 3.5 Profiler tests (label `checkpoint`)

1. Tokens bitwise identical with profiling on vs off (the tap already proved
   the pattern; events must not change replay semantics).
2. Timestamps monotone and non-overlapping in walk order (in-order list ⇒
   kernel *i* ends before *i+1* starts).
3. Σ per-kernel durations ≤ 1.001 × fence wall, and the gap (wall − Σ) is
   printed and recorded - the first in-situ dispatch-cost measurement.

### 3.6 Deliverable

`docs/15-step-anatomy.md`: the full 645-launch anatomy at depth 4096 -
per-family in-situ totals beside the probe-transplant floors (the first time
the two can be compared), the measured dispatch gap, and the re-ranked lever
ladder that Stage 1 executes. Every number labelled; the bench-vs-profile
distinction stated at the top.

## 4. Stage 0b - the vLLM cross-check (before any kernel change)

Per the protocol recorded in docs/14 (§cross-check): run vLLM greedy,
temperature 0, 32 tokens, on the three committed prompts, in the container
`vllm-xpu-env-next-p314-t214-vxkp0` on the box; compare ids three ways.
Engine == oracle is already proven, so the readings are: vLLM agrees with
both → the chain is closed end-to-end; vLLM disagrees with both → **suspect
`tools/oracle/dequant.py` first, freeze all kernel work until resolved**
(docs/14's own ruling). Outcome recorded in docs/14 either way. This runs
before any retune so every later divergence has a clean three-way baseline.

## 5. Stage 1 - the lever ladder

Initial ranking below; **docs/15's profile re-ranks it before lever 1
starts**, and a lever whose measured share cannot repay its cost is skipped
with a one-line ruling. Every lever is its own task with the same acceptance:

- full suite green, golden gate 96/96 (hard, §2);
- profiler before/after for the targeted family (the attribution);
- proxy check during iteration: tg64 @ depth 4096, single run (fast);
- on acceptance: full tg256 @ 4096 median-of-3 → BENCHMARKS.md row, sha
  naming the measuring binary; docs/12 mechanism section updated with the
  change *and* its in-situ number;
- a lever that misses its bar is reverted (single revert commit), the
  attempt and its measurement recorded in docs/15.

**L1 - `prep_res_norm` two-stage reduction.** 129 launches; 128 are SP16,
each a *single work-group* folding 16 × 5120 fp32 partials (320 KB) plus the
residual through one Xe core - the risk docs/12 wrote down when the kernel
landed, with the two-stage fallback already sketched there: stage A, P
work-groups each folding a partials slice and the residual add for its chunk;
stage B, one work-group finishing the RMS reduction over stage-A sums and
writing `x`. Fixed tree, fixed P ⇒ deterministic; the bf16 fold order changes,
so the golden gate is the acceptance instrument (§2). Expected yield if the
~40 µs/launch hypothesis holds: several ms (estimated - the family's traffic
is worth ~0.67 ms at bandwidth).

**L2 - `a‖b` GEMV.** `{K 5120, N 128 (pad from 96), S 1}` bf16 → grid
N/64 = **2 work-groups**, 48 launches/token: the most under-occupied kernel
in the step; hypothesis latency-bound. In-lever scope: WG/subgroup remapping
for tiny N (e.g. 32 columns per WG → 4 WGs, or K-split with a fixed 2-stage
sum). Folding a‖b into `gdn_step`'s prologue (it reads the same `x`) is a
redesign - memo only.

**L3 - `gdn_step` occupancy/tiling.** 48 × 4 grid = 192 WGs, SLM 6912 B,
GRF 128, no spills (measured, Task 4). If its in-situ share is large:
`CHUNK_V` 32 → 16 (384 WGs), GRF mode, SIMD width - retunes inside the
existing recurrence structure only; the reference comparison (state ≤ 1e-5,
out ≤ 1e-3, ring bit-exact) re-runs per variant.

**L4 - GEMV S/layout retune, in-situ.** The probe's picks were made in
isolation; the profiler prices them in the replayed step (different L2
history). Sweep S per shape against in-situ numbers. The split-K table
guards (capture `check_sizes`, landed 50bcc01) force the four baked consumer
constants to move with the table - a mismatch throws at capture. Changing
`Down`/`OutProj` S also resizes `prep`'s fold; L1 and L4 therefore interact,
and whichever runs second re-measures the other's family.

**L5 - attention SLM-staging.** Only if the profile contradicts the 2.314 ms
estimate upward. Otherwise: memo.

## 6. The gate

After the ladder: full bench, idle box, median-of-3.

- **≥ 31.50 t/s:** record the row, update README ladder row 1 and docs/05's
  verdict paragraph, tag `spec1.5-done`, close.
- **Short:** write `docs/superpowers/specs/2026-08-25-spec1.5-reassessment.md`:
  measured yield per lever (accepted *and* reverted), the remaining gap, and
  the redesign menu - norm→GEMV prologue fusion, `a‖b`→`gdn_step` fusion,
  SLM-staged attention, layout changes, context-bucketed lists - each priced
  from docs/15 with expected yield, correctness-risk, and which proofs it
  re-opens. The memo goes to the user; spec 1.5 extends or closes by that
  decision. A short close still updates every record honestly (phase-1
  discipline).

## 8. Constraints (binding, carried from spec 1 unless noted)

- Golden gate 96/96 hard; suite green; determinism discipline (§2).
- Per-op bf16 RNE discipline in any restructured kernel; subnormal f16
  scales decoded exactly; `-cl-denorms-are-zero` forbidden (build enforces);
  `-cl-fp32-correctly-rounded-divide-sqrt` remains the ocloc default.
- C++17, `-Wall -Wextra -Werror`; Linux only; the server never downloads.
- Box workflow: `tools/box.sh`, JOBS=44; verify recompiles after sync (both
  mtime traps are recorded - forward *and* revert direction).
- Profile mode never produces a bench row; bench rows name the sha of the
  measuring binary; every number labelled measured vs estimated.
- Work directly on `main`; nothing pushed; tags local.
- docs/12 mechanism explanation updated in the same commit as any kernel
  change (house rule: no code without mechanism).

## 9. Out of scope

MTP / speculative decode (spec 3); prefill, tokenizer, HTTP/SSE (spec 2);
prefix caching (queued after spec 3); multi-GPU / P-D disaggregation; loader
or checkpoint-format changes; `lm_head` requantisation; and every §6 memo
item until the gate rules on it.

## 10. Risks, stated

- **The bucket may not compress to 0.935 ms** (§1 arithmetic) - the gate and
  memo exist for exactly this; the spec's value is the measured decomposition
  either way.
- **In-situ GEMV above the floor** flips budget from the bucket to L4 -
  handled by re-ranking, not a surprise.
- **Timestamp quality:** 32-bit kernel timestamp wrap and timer resolution
  on BMG are handled in one helper (§3.1) and cross-checked by test 3's
  Σ-vs-wall identity; if the identity fails, the profiler is wrong, not the
  step.
- **The cross-check may fail** - that is a feature: it fires before any
  kernel changed, and docs/14 already names the prime suspect (dequant path).
- **L1×L4 interaction** (S resizes prep's fold) - ordered re-measurement is
  part of both levers' acceptance, not an afterthought.
