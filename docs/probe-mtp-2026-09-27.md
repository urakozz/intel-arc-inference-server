## 1. The head's wiring, from the reference

Reference: vLLM 0.29.1rc1 in the oracle image (`vllm-xpu-env-next-p314-t215-vxkp0`),
`vllm/model_executor/models/qwen3_5_mtp.py` (the registry maps `Qwen3_5MTP` to
it, `registry.py:700`; `config/speculative.py:916-927` picks it for this
checkpoint's `Qwen3_5ForConditionalGeneration`).

| question | answer | where |
|---|---|---|
| input token | `embed(x[t+1])` through `pre_fc_norm_embedding` | `qwen3_5_mtp.py:162` |
| input hidden | the main model's hidden at t **after its final norm** (the target's returned `hidden_states`), through `pre_fc_norm_hidden` | `qwen3_5_mtp.py:163`; `qwen3_next.py:729` (`hidden_states, _ = self.norm(hidden_states, residual)`) |
| `fc` order | `cat([embed, hidden])` - **embed first** | `qwen3_5_mtp.py:164` |
| layer | one `Qwen3_5DecoderLayer(layer_type="full_attention")`, its own KV | `qwen3_5_mtp.py:177` |
| output | `mtp.norm(y)` - the returned hidden is **post-norm**; logits = shared `lm_head` | `qwen3_5_mtp.py:188`, `:308` |
| position | the draft for (h_t, x[t+1]) runs at **position t**; each chained step +1 | `v1/spec_decode/llm_base_proposer.py:839` ("rotate the input ids and leave the positions unchanged") |
| chaining | step i+1 takes step i's returned (post-`mtp.norm`) hidden as `h` | `llm_base_proposer.py:759-764` |

**Spec correction:** spec 8 §3.2 says `h_t` "before the final norm"; the
reference feeds the hidden **after** it. In the engine that is `b.x` after a
step (the final-normalised row `lm_head` reads), not `b.resid`.

Norms are the zero-centred `(1 + w)` RMSNorm (`Qwen3_5RMSNorm`). The reference
head is `tools/oracle/mtp_ref.py`; `tools/oracle/test_mtp_ref.py` checks the 15
tensors against doc 03 (shapes, bf16, 0.849 GB), a 16-token depth-3 chain
finite, and the explicit attention against transformers' own decoder layer:
depth 1 cosine 0.999984, chained depth-2 rows 0.999984 to 0.999995. ALL PASS.

### The wiring controls (depth-1 greedy acceptance, same rows)

`mtp_accept.py --controls`: the same head at depth 1 on the same rows, with one
thing changed each time. The rows are continuation rows only.

| source | ref | pre-norm hidden | swapped `cat([hidden, embed])` | layer at t+1 |
|---|---:|---:|---:|---:|
| golden/code | **241/256** 0.941 | 230/256 0.898 | 1/256 0.004 | 241/256 0.941 |
| golden/prose | **202/256** 0.789 | 196/256 0.766 | 0/256 0.000 | 201/256 0.785 |
| golden/cjk | **187/256** 0.730 | 176/256 0.688 | 2/256 0.008 | 186/256 0.727 |
| toolcall (4 sources) | **598/607** 0.985 | 596/607 0.982 | 1/607 0.002 | 598/607 0.985 |

- **The concatenation order is proven.** Swapping it drops acceptance to
  about 0, a wide margin.
- **Post-norm beats pre-norm on every source, but only by 1 to 4 points.**
  That is not the wide margin Review Focus 1 asked for. The reason: the
  final norm and `pre_fc_norm_hidden` are both RMSNorms, so the pre-norm
  hidden differs from the reference only by the final norm's per-channel
  weight. The citation above is what settles it, and the numbers agree with
  it.
- **The position control cannot discriminate, and it cannot in principle.**
  Moving the head's layer to t+1 moves every query and every key by the same
  +1. RoPE depends only on the query-key distance, so this is exact up to
  rounding. What matters is that every depth-1 entry in the head's KV uses
  the same convention and each chained step adds 1. 8b must copy the
  reference's convention (position t) so the M1 gate compares like with
  like.

## 2. Acceptance by depth

**The opencode log is not recorded yet** (`tests/golden/opencode/session1/`
is absent; plan 7a is producing the tooling). The agentic numbers below come
from the plan's fallback source: the A4 tool-call set's bf16 oracle outputs
(`~/b70-toolcall/toolcall-out/*.bf16.ids`), 4 scenarios, 607 output tokens,
each with the last 2048 ids of its prompt as context. To rerun on the log once
it exists, use one command on the box:

    tools/oracle/run_in_container.sh 'python3 tools/oracle/mtp_accept.py "$SNAP" \
        --opencode /ws/tests/golden/opencode/session1 --out /ws/oracle-out-spec8a/accept_opencode.json'

`--opencode` takes the longest turns up to 2000 output tokens, uses
`prompt_ids[-2048:]` as context, and uses the requests' own
temperature/top_p/top_k when present.

**Sampling parameters:** `temperature 1.0, top_p 0.95, top_k 20`, from the
checkpoint's `generation_config.json` (`do_sample: true`). The plan's fallback
text says 0.6, but it also says to read the file and use its values, and 1.0
is what the file says.

**The golden prompts** are the three prompts plus 256 greedy ids from the
engine (`b70-decode --n 256`, device 0). The teacher-forced forward is the
dequantised CPU oracle (`mtp_ref.build_main`, the same model as the golden
gate).

The method is in `mtp_accept.py`'s docstring. In short:
- **Greedy:** depth d > 1 is conditional. A row counts only when depths
  1..d-1 were accepted and the text agrees with them.
- **Sampled:** each depth's number is the exact `Σ min(p, q)`. Depth d > 1 is
  conditioned on the previous draft having been accepted as the text's token.
- **Chaining:** every chained step runs on the head's own hidden (Review
  Focus 5).

## 3. The verify step at M = 1..4, draft, commit and round trip

`tools/probe/probe_verify_m`, device 0, built with `-DB70_DECODE_EXTRA_M=ON`.
Setup: prefill 4096 ids, then capture the REAL decode list at each M
(774 kernels and 19 modules at every M). Each arm rewinds `pos` to 4096, runs
8 warm-up replays, then times 64 replays, each an execute plus a fence. There
are 3 rounds, rotated interleaved order, after a 32-replay warm-up burst.
Two runs: 17:12 (load 4.9) and 17:45 (load 8.8, `uptime`, with a CPU oracle
run active on the host). The table shows run 2; run 1 agrees within 0.3%.

**The spec's assumption of 1.05-1.15 steps for a verify does not hold past
M = 2.** There are two reasons, and both are levers for 8b:
- The int4 GEMV jumps +9.3 ms from M = 2 to M = 3, against +2.3 ms from
  M = 1 to M = 2.
- `attn_decode` is linear in M: each row re-walks the 4096-position KV.

The bf16 `lm_head` is the only family that really reads its weights once for
all M rows.

Pageable costs 2.5x that, so 8c reads them into L0 host memory.

## 4. The decision

- **K = 3 provisionally** (the highest derived speedup on the agentic
  fallback source: 1.696x greedy, 1.685x sampled). This is not robust:
  - On free text (golden) K = 1 wins (1.345x), and K = 3 falls to 1.249x.
  - The break-even is set by the M = 3 GEMV jump.
  - Rerun `mtp_accept.py --opencode` when the log exists, and apply the
    same rule to its rows.
  - `--mtp K` stays runtime-selectable in 1..3 (spec 8 §3.6), so 8b must
    capture and gate every K, not only 3.
  - The cheapest lever is the M = 3/4 int4 GEMV variant: it moves K = 3
    more than anything else.
- **Commit mechanism: the `Control` index.** The 151 MB slot copy measures
  0.565 ms, 1.66% of a step, above the plan's 1% bar. 8b makes the live GDN
  state slot an index the kernels read from `Control`, instead of copying
  slot j into `gdn_state`.
- **Stopping rule: not triggered, provisionally.**
  - Greedy depth-1 acceptance is 0.985 on the fallback agentic outputs and
    0.820 on the golden prompts, both above the 0.5 bar. The bar is defined
    on the opencode outputs, which are pending.
  - The M = 2 verify is 1.171 plain steps, below the 1.5 bar.
  - Proceed to 8b. Recheck the acceptance bar on the opencode log.

## 5. The capture refactor is neutral

a member set from it. `B70_DECODE_EXTRA_M` defaults to OFF, so a default
build compiles no new binary; the `gemv` production cells now apply at every
M, and no default M > 1 variant matches one.
